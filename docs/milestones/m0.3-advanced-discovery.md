M0.3 turns Discovery from a make-and-model search into a search with criteria: the user can
state requirements and preferences, give them priorities, and see which vehicles meet the
requirements, which come close, and why each result is where it is.

This document turns the approved M0.3 product decisions into a specification. It does not
redesign them. Where the decisions, the acceptance matrix, the existing documentation or the code
disagree or leave a gap, the point is recorded in [§17 Open issues](#17-open-issues) and not
settled here. Statements marked **Proposal** are technical choices that do not change product
behaviour (class C in [§17](#17-open-issues)); they become binding when this specification is
approved.

Normative words: **must** is a requirement; **should** is a recommendation an implementation may
depart from with a stated reason; **may** is permitted.

## 1. Goal and rationale

M0.2 proved one end-to-end path (Discovery → Vehicle Analysis → DC simulation) with a direct
search by make or model. Discovery could not yet express needs. M0.3 adds the missing half of
the Discovery activity described in the [user flows](../ux/user-flow-overview.md#discover): text
search and criteria in one continuous loop, with results that explain themselves.

The milestone is deliberately narrow: four criteria whose data the catalogue already holds
(price, seats, body type, peak DC power). It establishes the evaluation model (requirements that
exclude, preferences that order, near matches with a bounded tolerance, explicit priorities) on a
small, verifiable base, so that later criteria (range, charging time, trips) can be added on the
same model without changing its meaning.

## 2. Product Vision alignment

| Product Vision principle                                      | How M0.3 applies it                                                                                                                                 |
| ------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| Complexity available, never mandatory (§1)                    | No criterion is active at first; `/cerca` opens on the whole catalogue as in M0.2. Numeric details of the ranking appear only on request (§10.4).   |
| Direct access, without unnecessary guidance (§3.1)            | No questionnaire, wizard or onboarding. Criteria are added from one command, in any order, while results stay visible.                              |
| Needs before technical specifications (§3.2)                  | Practical criteria (price, seats, body type) and a technical one (peak DC power) coexist in one panel; no mode separates beginners from experts.    |
| Progressive depth (§3.3)                                      | Concrete reasons on each card first; weights, satisfactions and distances behind "Perché questo risultato?".                                        |
| Transparent recommendations (§3.6)                            | Every position is traceable to the user's criteria and the vehicle's data; missing data is stated, never filled in; the score is not a probability. |
| Respect for user autonomy (§3.7)                              | Priorities are the user's, explicit and editable. No automatic suggestion to relax a requirement.                                                   |
| Technical accuracy over convenient simplifications (UX §8)    | Peak DC power is presented as a peak specification, never as a charging time or charging performance.                                               |
| Return to the original comparison without losing context (§4) | The whole Discovery state lives in the URL and survives opening a vehicle and coming back (§11).                                                    |

The [UX Design Principles](../ux/design-principles.md) apply in full, in particular §1, §2 and §6:
no instructional copy for self-evident interactions, no copy written to demonstrate the Product
Vision, no control added only because it is available.

## 5. Criteria model

### 5.1 The four criteria

| Criterion          | Code (proposal) | Default mode | Value                               | Vehicle attribute                       |
| ------------------ | --------------- | ------------ | ----------------------------------- | --------------------------------------- |
| Prezzo             | `price`         | Requirement  | A price in euros, integer, `t > 0`  | List price, `listPriceEur`              |
| Posti              | `seats`         | Requirement  | A number of seats, integer, `t ≥ 1` | `seats`                                 |
| Carrozzeria        | `body`          | Preference   | A non-empty set of body types       | `bodyType`                              |
| Potenza DC massima | `dc`            | Preference   | A power in kW, integer, `t > 0`     | Peak DC power, `peakDcPowerKw(vehicle)` |

The input domains (bounds, integer steps) are proposed in [§12.2](#122-invalid-and-incomplete-input-fr-32)
and [OI-07](#oi-07--input-domains-and-editor-commit-timing). The body-type vocabulary is
[OI-06](#oi-06--body-type-vocabulary).

### 5.2 Rules (FR-01 to FR-08)

- **FR-01 Initial state.** No criterion is active when Discovery opens without `s`.
- **FR-02 Uniqueness.** Each criterion can be active at most once, in one mode. "Aggiungi
  criterio" offers only inactive criteria; with all four active it offers none (it may be hidden
  or disabled, an implementation choice). No state, transition or URL can produce a duplicate.
- **FR-03 Default mode.** A newly added criterion enters its default mode (table above) at the end
  of that mode's priority order.
- **FR-04 Mode switch.** Any criterion can move between requirement and preference. The value is
  kept unchanged; the criterion is placed at the end of the new mode's order; the relative order of
  the others is unchanged in both modes. For Posti the same value changes meaning (§6.1).
- **FR-05 Reordering.** Within a mode, criteria can be reordered directly (pointer drag) and with
  an equivalent keyboard-operable alternative. Reordering changes priorities and weights, never
  values or modes. Reordering across the two modes is not a reorder; it is a mode switch (FR-04)
  through its own control. **Proposal:** dragging is limited to the criterion's own section.
- **FR-06 Removal.** Each criterion can be removed individually; the others keep their relative
  order.
- **FR-07 "Cancella tutti i criteri".** Removes every criterion and keeps the text query. Its
  effect on the sort order is [OI-04](#oi-04--what-the-reset-commands-reset).
- **FR-08 "Ripristina ricerca".** Clears the text query and every criterion and shows the initial
  catalogue (AC-10). Its effect on the sort order is [OI-04](#oi-04--what-the-reset-commands-reset).

### 5.3 Priorities

The order of each list is the priority: position 1 is the highest. Requirements and preferences
have separate orders and separate weights (§7.1). The order is always explicit in the interface;
weights are never edited directly (no percentages to type).

### 5.4 Text search and criteria

The text query is applied first, with the M0.2 rules: the candidate set is the catalogue vehicles
whose name matches `q`. Criteria are evaluated only on the candidates (FR-09). The query is not a
criterion: it has no mode, priority or weight and is not part of `s`.

### 5.5 Committed state and drafts (FR-10)

The **committed** Discovery state is the one the URL represents (ADR 0001 Decision 2, principle
1). Editors work on a **draft**, which is local React state:

- A criterion just added, without a valid value, is a draft. It is visible in its section but is
  not committed, does not take part in the evaluation, does not count in the weights and is not in
  the URL. There are no default values for criteria: the product does not choose a budget, a
  number of seats, a body type or a power on the user's behalf.
- Editing a committed criterion creates a draft of it. While the draft is incomplete or invalid
  (empty field, non-integer, out of domain, no body type selected), the committed criterion, the
  results and the URL stay unchanged (AC-39). The editor shows that the value is not valid.
- A valid draft value is committed: the results update and the URL is rewritten. Commit timing
  (each valid change, a pause, blur or Enter) is [OI-07](#oi-07--input-domains-and-editor-commit-timing);
  whatever is chosen, no mandatory confirmation button is introduced (ADR 0001 Decision 2).
- Drafts are transient UI: they are not preserved across navigation (ADR 0001 Decision 4). When
  the URL changes from outside (Back, Forward, a link), drafts are discarded and the editors show
  the committed state.
- Add, remove, mode switch, reorder, clear and reset act on the committed state at once when they
  concern committed criteria. A mode switch or reorder of a draft only changes the draft.

## 6. Requirement and preference semantics

### 6.1 Per criterion (FR-11)

| Criterion       | As a requirement, satisfied when        | As a preference, better when                    |
| --------------- | --------------------------------------- | ----------------------------------------------- |
| Prezzo `t`      | `price ≤ t` (maximum price)             | the price is lower (§7.3)                       |
| Posti `t`       | `seats ≥ t` (at least `t` seats)        | the number of seats is exactly `t` (§7.4)       |
| Carrozzeria `T` | `bodyType ∈ T` (any accepted body type) | `bodyType ∈ T` (any preferred body type) (§7.6) |
| Potenza DC `t`  | `peakDc ≥ t` (minimum peak power)       | the peak power is higher (§7.5)                 |

### 6.2 Combination (FR-12)

- Several body types in one criterion are combined with **OR**.
- Different requirements are combined with **AND**: a vehicle is compatible only if it satisfies
  all of them.
- **Preferences never exclude a vehicle**, whatever their satisfaction (AC-18). They only order.
- Requirement priorities **do not make a requirement optional**. They weigh the distance of near
  matches (§7.7) and nothing else.

### 6.3 Peak DC power

The criterion is the manufacturer-type peak DC power already shown on the card ("Potenza DC
massima", `costruttore`). The interface must not describe it as a charging time, a charging
speed in practice or a session outcome, and must not derive one from it (UX principle 8; the
wireframe README's distinction between the technical filter and the practical charging-time
criterion). The charging-time criterion is out of scope (§18).

## 7. Evaluation engine: formulas and parameters

All values are computed unrounded; only presentation rounds (§10.5). Comparisons at decision
boundaries follow §7.10.

### 7.1 Weights (FR-13)

For a list (requirements or preferences) of `n ≥ 1` committed criteria, the criterion at position
`i` (1-based) has weight

```text
w_i = (n − i + 1) / (n(n + 1) / 2)
```

The weights are positive, strictly decreasing with the position and sum to 1. The two lists are
weighted independently. Since at most four criteria are active, `n ≤ 4`:

| n   | Weights (position 1 → n) |
| --- | ------------------------ |
| 1   | 1                        |
| 2   | 2/3, 1/3                 |
| 3   | 3/6, 2/6, 1/6            |
| 4   | 4/10, 3/10, 2/10, 1/10   |

Weights are not configurable in M0.3.

### 7.2 Preference score (FR-14)

```text
S(v) = Σ_j w_j · f_j(v)        over the active preferences j
```

Each satisfaction function `f_j` returns a value in [0, 1] and is independent of the weight and
of the catalogue (it depends only on the vehicle's attribute and the criterion's value). `S(v)` is
in [0, 1]. With no active preference, `S` is undefined: it is not shown and is skipped in the
ranking (§9.1).

`S` is a ranking score derived from the user's stated preferences. It must not be presented as a
probability, a percentage of compatibility or an objective measure of suitability.

### 7.3 Price preference, `f_price`

Decreasing, piecewise linear, saturated. For price `x` and value `t`:

```text
x ≤ 0.8t          → 1
0.8t < x ≤ t      → 1 − 0.30 · (x − 0.8t) / (0.2t)
t < x < 1.2t      → 0.70 · (1.2t − x) / (0.2t)
x ≥ 1.2t          → 0
```

Anchor points: `0.8t → 1`, `t → 0.70`, `1.2t → 0`.

### 7.4 Seats preference, `f_seats`

Maximum at the exact number, asymmetric. For seats `s` (an integer) and value `t`:

```text
s = t       → 1
s = t + 1   → 0.5
otherwise   → 0     (s ≤ t − 1 or s ≥ t + 2)
```

Seats are integers (the catalogue validates them), so no interpolation occurs. This function
applies only to the preference; as a requirement Posti means "at least `t`".

### 7.5 Peak DC power preference, `f_dc`

Increasing, piecewise linear, saturated. For peak power `x` (kW) and value `t`:

```text
x ≤ t − 50          → 0
t − 50 < x ≤ t      → 0.60 · (x − (t − 50)) / 50
t < x < t + 100     → 0.60 + 0.40 · (x − t) / 100
x ≥ t + 100         → 1
```

Anchor points: `t − 50 → 0`, `t → 0.60`, `t + 100 → 1`.

### 7.6 Body type preference, `f_body`

Categorical: `1` if the vehicle's body type is one of the selected types, `0` otherwise. Selected
types are equivalent; there is no similarity between types.

### 7.7 Requirement distances (FR-15)

For each numeric requirement, the unfavourable deviation `Δ_i(v) ≥ 0` and the tolerance `τ_i`:

| Requirement      | `Δ_i(v)`             | `τ_i`      |
| ---------------- | -------------------- | ---------- |
| Prezzo `≤ t`     | `max(0, price − t)`  | `0.20 · t` |
| Posti `≥ t`      | `max(0, t − seats)`  | `2` seats  |
| Potenza DC `≥ t` | `max(0, t − peakDc)` | `50` kW    |

```text
d_i(v) = min(1, Δ_i(v) / τ_i)
```

A satisfied requirement has `d_i = 0`. Carrozzeria as a requirement has no distance: it is
satisfied (`d = 0`) or violated, and a violation excludes the vehicle (§8.2).

With these tolerances one missing seat gives `d = 0.5` and two give `d = 1`.

### 7.8 Overall distance `D` and mean violation severity `V` (FR-16)

With the requirement weights `w_i` (§7.1) and `B(v)` the set of requirements `v` violates:

```text
D(v) = Σ_i w_i · d_i(v)                       over all active requirements
V(v) = Σ_{i∈B(v)} w_i · d_i(v) / Σ_{i∈B(v)} w_i    defined only when B(v) is not empty
```

`D` includes the satisfied requirements (contributing 0); it ranks near matches and explains the
distance from the whole request. `V` is the weighted mean over the violated requirements only; it
decides admissibility. `D` is not an admissibility condition and `V` is not a ranking key.

### 7.9 Calibration parameters (FR-17)

Approved as the initial calibration. They must be defined in one module, named, documented next to
their definition and covered by tests, so that a later recalibration is one change.

| Parameter                                 | Value        |
| ----------------------------------------- | ------------ |
| Price preference: full satisfaction at    | `0.8 t`      |
| Price preference: satisfaction at `t`     | `0.70`       |
| Price preference: zero satisfaction at    | `1.2 t`      |
| Seats preference: satisfaction at `t + 1` | `0.5`        |
| DC preference: zero satisfaction at       | `t − 50` kW  |
| DC preference: satisfaction at `t`        | `0.60`       |
| DC preference: full satisfaction at       | `t + 100` kW |
| Price tolerance `τ_price`                 | `0.20 · t`   |
| Seats tolerance `τ_seats`                 | `2` seats    |
| DC tolerance `τ_dc`                       | `50` kW      |
| Admissibility threshold on `V`            | `V ≤ 0.25`   |
| Page size per section                     | `20`         |

### 7.10 Numerical precision at boundaries (FR-18)

The matrix requires the boundary handling to be formalised. **Proposal:**

- Requirement satisfaction compares the raw attribute with the raw value (`price ≤ t`,
  `seats ≥ t`, `peakDc ≥ t`); these are exact for the integer domains of §12.2.
- Derived ratios used in decisions or ranking (`d_i` against 1, `V` against 0.25, `S` and `D` as
  ranking keys) are compared after quantisation to a fixed step `ε = 10⁻⁹`
  (`round(x / ε)`), defined once with the calibration. Quantising, rather than comparing with a
  tolerance, keeps the sort comparators transitive.
- A value mathematically equal to a threshold is therefore on the threshold: `V = 0.25` is
  admissible, `d = 1` is not (AC-21: €42,000 and €48,000 against €40,000).
- Displayed values are rounded separately (§10.5) and never feed back into decisions.

## 8. Compatibility and near compatibility

### 8.1 Pipeline (FR-19)

1. Candidates: the catalogue vehicles matching `q` (§5.4).
2. Each candidate is classified as **compatible**, **near-compatible** or **excluded** (§8.2).
3. Compatible and near-compatible vehicles are shown in two separate sections; excluded vehicles
   are not shown and there is no "non valutabili" section.
4. Each section is ordered (§9) and paginated (§9.3).

A vehicle belongs to exactly one class; no vehicle appears in both sections.

### 8.2 Classification (FR-20)

For a candidate `v` and the committed requirements, in this order:

1. If any attribute needed by an active requirement is missing → **excluded**.
2. If `v` violates no requirement → **compatible**. With no requirement active, every candidate
   is compatible.
3. If `v` violates a Carrozzeria requirement → **excluded**.
4. If any violated numeric requirement has `d_i ≥ 1` → **excluded**.
5. If `V(v) ≤ 0.25` → **near-compatible**; otherwise → **excluded**.

Preferences never take part in the classification (AC-18, AC-26: reordering preferences never
changes membership). Reordering requirements changes their weights and therefore `D` and `V`, so
it can change which vehicles are near-compatible (AC-26).

Consequences of the approved rule, stated so that tests and reviewers expect them:

- A single seats violation is never admissible on its own (`d ≥ 0.5`, AC-22).
- Because `V` averages only the violated requirements, adding a second, small violation can make
  a vehicle admissible that would be excluded with the first violation alone. This is
  [OI-01](#oi-01--a-second-violation-can-make-a-vehicle-admissible).

## 9. Ranking, manual sorting and pagination

### 9.1 "Più pertinenti" (default) (FR-21)

Compatible section, keys in order:

1. `S` decreasing (skipped when no preference is active);
2. list price increasing;
3. vehicle name (`make model`) increasing, `it-IT` collation;
4. vehicle ID increasing (code-unit order).

With no preference active this is the M0.2 order (price, name, ID), so `/cerca` without criteria
satisfies AC-01.

Near-compatible section, keys in order:

1. number of violated requirements increasing;
2. `D` increasing;
3. `S` decreasing (skipped when no preference is active);
4. list price increasing;
5. name increasing;
6. ID increasing.

### 9.2 Manual sort orders (FR-22)

| Sort (label)             | Code (proposal) | Keys after the main one    |
| ------------------------ | --------------- | -------------------------- |
| Più pertinenti (default) | `rel`           | §9.1                       |
| Prezzo crescente         | `price-asc`     | name, ID                   |
| Prezzo decrescente       | `price-desc`    | name, ID                   |
| Potenza DC decrescente   | `dc-desc`       | price increasing, name, ID |
| Marca e modello A–Z      | `name`          | price increasing, ID       |

Rules:

- A manual sort orders each section separately; it never moves a vehicle between sections.
- Tie-breaks are price increasing, name, ID, omitting the key already used as the main key.
- A vehicle missing the attribute of a sort key goes after every vehicle that has it, within its
  section, for that key (AC-32); among themselves such vehicles are ordered by the following keys.
  In the current catalogue only peak DC power could be missing in future data; price and name are
  always present.
- Changing the sort returns both sections to page 1 (AC-31).

### 9.3 Pagination (FR-23)

- 20 vehicles per page, per section; the two sections are paginated independently (AC-34).
- The current page of each section is in the URL (§11.2).
- Changing the query, any committed criterion (add, remove, value, mode, order, clear, reset) or
  the sort returns both sections to page 1. That a query change also resets the pages is part of
  [OI-04](#oi-04--what-the-reset-commands-reset).
- A page beyond the last existing page shows the last page (the catalogue may have changed since
  the link was made, AC-36).
- **Proposal:** pagination controls appear only for a section with more than 20 vehicles.

### 9.4 Section presentation (FR-24)

- With at least one compatible and at least one near-compatible vehicle, the near-compatible
  section starts collapsed, with its count visible (AC-29).
- With no compatible and at least one near-compatible vehicle, it is expanded automatically
  (AC-28).
- Whether the expanded state is preserved across navigation is
  [OI-05](#oi-05--expanded-state-of-the-near-compatible-section).
- With no requirement active, no vehicle can be near-compatible. **Proposal:** the
  near-compatible section is then not rendered, and the list keeps the M0.2 presentation (count
  and results) without calling them "compatibili", because compatibility is vacuous without
  requirements ([OI-14](#oi-14--headings-without-requirements)).

## 10. Discovery UX and explainability

Composition follows the Active Criteria wireframe and Livrea Consolidated `02-discovery.svg` for
the parts in scope (§4.4), at 1440 px, the only designed width.

### 10.1 Layout

- Search field (M0.2) above or beside the criteria panel, as in the wireframe.
- Criteria panel: only the active criteria (committed and drafts), in two labelled sections,
  "Requisiti" and "Preferenze", each in priority order; "Aggiungi criterio"; "Cancella tutti i
  criteri" when at least one criterion is active.
- Results header: the count of the visible result set and the sort control.
- Section "Compatibili", then section "Quasi compatibili" (collapsible), each with its pagination.
- The global notice "Dati e veicoli illustrativi." stays.

### 10.2 Criterion editors

- Each active criterion shows its label and its current value in short form (for example "fino a
  €40.000", "almeno 5 posti", "esattamente 5 posti" as a preference, "SUV medio o Station wagon",
  "almeno 150 kW"). Exact copy is an implementation choice within the UX principles.
- Opening a criterion shows its contextual editor: the value control, the Requisito/Preferenza
  behaviour toggle, and the remove action.
- Each criterion has a drag handle for its section and a keyboard-operable way to move it up and
  down (FR-05, AC-41). The effect of either is identical (same state, same URL).
- Editing follows §5.5. An invalid value is shown as invalid in the editor; it never changes the
  results.

### 10.3 Visual identity rules applied

Livrea Consolidated's consolidated decisions apply without a new design system:

- Criteria and their behaviour are scenario parameters: yellow tabs on active criteria, the
  selected behaviour option in yellow with an ink outline, as in `02-discovery.svg` (variant B).
- The sort control, pagination, section toggle, "Perché questo risultato?", "Aggiungi criterio",
  "Cancella tutti i criteri" and "Ripristina ricerca" are view options, navigation or actions:
  ink, never yellow.
- A violated requirement on a near-compatible card is a signal: icon and words, signal colour,
  never yellow and never colour alone. The URL recovery notice is a signal too (the existing
  `SignalNotice` or `PageNotice` components should be reused).
- Vehicles in Discovery are outside any comparison: neutral, no slot colour.
- Tokens only; no raw colour in components; Schibsted Grotesk only.

### 10.4 Explanations (FR-25)

Two levels (AC-40):

**Level 1, on every card, always visible: concrete reasons.** Short statements built from the
vehicle's values and the user's criteria, never from scores:

- For a near-compatible vehicle, every violated requirement with the vehicle's value and the gap
  (wireframe: "REQUISITO NON RISPETTATO · Budget: €46.800: €1.800 oltre il limite").
- For a compatible vehicle, the criteria it meets, with the vehicle's value, compactly; the
  preferences that most contributed may be named.
- A missing attribute is stated as not available ("Potenza DC non disponibile"), never replaced by
  a value or hidden.

**Level 2, on request, "Perché questo risultato?":** a disclosure on the card showing, per active
criterion: the vehicle's value (with its provenance tag), the criterion's value, the mode and
position, and

- for a preference: satisfaction `f_j`, weight `w_j`, contribution `w_j · f_j`, and the total `S`;
- for a requirement: met or violated, distance `d_i`, weight `w_i`; for a near-compatible vehicle
  also `D`, `V` and the number of violations, which determine its position.

The disclosure is a button with an expanded state; its content is text, reachable by keyboard and
screen readers. It is transient UI (not preserved on navigation).

### 10.5 Number presentation

**Proposal** (see [OI-13](#oi-13--presentation-of-the-ranking-numbers)): `it-IT` formatting;
satisfactions, distances, `S`, `D` and `V` with two decimals ("0,85"); weights as shares of the
list's total, rounded to whole percent ("50%"), explicitly labelled as weights. The score is never
written as a percentage. Prices and power use the M0.2 formats.

### 10.6 Feedback

- The results header is a polite live region, as in M0.2: committed changes announce the new
  counts.
- A reorder announces the criterion's new position.
- No "effect of the last change" notice and no undo (wireframe elements out of scope).

## 11. URL, navigation and context

### 11.1 Ownership

The committed Discovery state is owned by the URL (ADR 0001 Decision 1). It is rebuilt from the
URL alone, with no storage, history state or store. Drafts, open editors, disclosure state and
hover are local and transient. **No Redux store is introduced**: M0.3 has no shared state that the
URL or a component does not already own.

### 11.2 Parameters (FR-26)

| Parameter | Meaning                                                   | Default (omitted) | Validation                                       |
| --------- | --------------------------------------------------------- | ----------------- | ------------------------------------------------ |
| `q`       | Text query, as in M0.2                                    | empty             | M0.2 rules (single, ≤ 100 characters after trim) |
| `s`       | Advanced state: criteria, values, modes, priorities, sort | default state     | §11.3, §11.4                                     |
| `pc`      | Page of the compatible section (proposal name)            | 1                 | single positive integer, canonical decimal       |
| `pq`      | Page of the near-compatible section (proposal name)       | 1                 | single positive integer, canonical decimal       |

Canonical serialisation: parameters in the order `q`, `s`, `pc`, `pq`; each omitted when at its
default. `/cerca` is therefore the M0.2 initial URL, and `/cerca?q=…` the M0.2 search URL.
Unknown parameters are ignored. The parameter names `pc` and `pq` are a proposal; `q` and `s` are
approved.

### 11.3 Encoding of `s` (FR-27)

Approved: canonical JSON, explicit version, Base64URL, no compression, deterministic.

**Proposal for version 1:**

```text
s = base64url( utf8( canonical JSON ) )        RFC 4648 §5 alphabet, no padding

{ "v": 1, "r": [Criterion…], "p": [Criterion…], "o": Sort }

Criterion = { "k": "price", "t": <integer> }
          | { "k": "seats", "t": <integer> }
          | { "k": "body",  "t": [<body type code>, …] }
          | { "k": "dc",    "t": <integer> }
Sort      = "price-asc" | "price-desc" | "dc-desc" | "name"
```

- `r` is the requirements list, `p` the preferences list; array order is the priority. Mode is
  given by the list, so a mode switch moves the entry; the value `t` keeps the same field in both
  modes (FR-04).
- Canonical form: keys in the order shown (`v`, `r`, `p`, `o`; `k`, `t`); no whitespace; integers
  without sign, exponent or leading zeros; body type codes without duplicates, in the codec's
  fixed order (alphabetical by code); `r`, `p` omitted when empty; `o` omitted for `rel`. The
  default state (no criteria, `rel`) has no `s` at all.
- Body type codes are the catalogue's stable codes (`compact`, `estate`, `midSizeSuv`, `mpv`,
  `sportsSedan`), not UI labels, so a label change never breaks a link.
- The decoder accepts any JSON that satisfies the schema (other key orders, whitespace, optional
  padding); the encoder always writes the canonical form. Parsing a serialised state yields an
  equal state (round trip, ADR 0001 Decision 1).
- `s` contains no free text (the query stays in `q`), so its JSON is ASCII.
- An `s` longer than 1,024 characters is treated as undecodable (a guard against abuse; a valid v1
  state is far shorter).

**Evolution.** `v` identifies the schema. Additive optional fields may be added within a version:
the v1 decoder ignores unknown keys at the top level and in criteria. An incompatible change
introduces `v: 2`; the decoder then keeps accepting v1 and maps it to the new model, so existing
links keep working. A version the decoder does not know is undecodable (§11.4).

### 11.4 Invalid URLs and partial recovery (FR-28)

Parsing never fails the page. It returns the recovered state and a list of typed issues
(errors as values). `q`, `s`, `pc` and `pq` are parsed independently: an invalid `s` never loses
a valid `q` (AC-38), and the reverse.

| Case                                                                                           | Result                                                                                    | Notice                                   |
| ---------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- | ---------------------------------------- |
| `s` repeated, too long, not Base64URL, not UTF-8, not JSON, not an object, `v` missing/unknown | Default advanced state (no criteria, `rel`)                                               | Yes                                      |
| A criterion malformed (unknown `k`, `t` of the wrong type or out of domain)                    | That criterion dropped; the others kept in their order (AC-37)                            | Yes                                      |
| A criterion duplicated (same `k` twice, or in both lists)                                      | First occurrence kept (scanning `r` then `p`), later ones dropped                         | Yes                                      |
| Body type list with some unknown codes                                                         | Unknown codes dropped; the criterion kept if at least one code remains, dropped otherwise | Yes                                      |
| Body type list with repeated codes                                                             | Repeats merged                                                                            | No                                       |
| `r` or `p` not an array                                                                        | That list treated as empty                                                                | Yes                                      |
| `o` unknown or of the wrong type                                                               | `rel`                                                                                     | Yes                                      |
| Unknown keys                                                                                   | Ignored (evolution)                                                                       | No                                       |
| `pc` / `pq` repeated or not a canonical positive integer                                       | Page 1                                                                                    | Yes                                      |
| `pc` / `pq` beyond the last page                                                               | Last page (§9.3)                                                                          | No                                       |
| `q` invalid                                                                                    | M0.2 behaviour: empty query                                                               | [OI-11](#oi-11--notice-for-an-invalid-q) |

- The notice is non-blocking (results remain usable), visible, announced politely, and says that
  some parameters of the link were not valid and have been ignored. It does not list technical
  details.
- **Proposal:** the URL is not rewritten on load; the next commit writes the canonical form of
  the recovered state, as the DC simulator does after an invalid URL. The notice disappears at
  that commit.

### 11.5 Navigation and context (FR-29)

- Opening a vehicle from a result (compatible or near-compatible) pushes the vehicle URL with the
  origin context, which now carries the whole committed Discovery state:
  `/veicoli/<id>?da=cerca&q=…&s=…&pc=…&pq=…` (each parameter only when not default).
- Vehicle Analysis' "‹ Risultati" and the browser's Back both restore query, criteria, values,
  modes, priorities, sort and pages (AC-35), plus native scroll restoration where it applies
  (M0.2). Both must behave consistently (ADR 0001 Decision 4).
- The DC simulator forwards the same origin parameters, as in M0.2; returning through it keeps the
  Discovery state.
- Origin parsing reuses the Discovery parser with its recovery: an invalid `s` inside an origin
  keeps the origin as "search" with the recovered state; only an invalid `da` (or the M0.2 cases
  for `q`) turns it into a direct visit, as today. **Proposal:** no recovery notice on Vehicle
  Analysis; the return link carries the canonical recovered state.
- Transient states (open editors, drafts, disclosures, hover) are not restored (ADR 0001 Decision
  4, M0.2 criterion 8.3).
- A shared Discovery URL opened in a new session reproduces the same configuration; the results
  depend on the current catalogue (AC-36).

### 11.6 History policy (FR-30)

Following ADR 0001 Decision 2:

| Event                                                                     | Results      | URL                   | History                                                                |
| ------------------------------------------------------------------------- | ------------ | --------------------- | ---------------------------------------------------------------------- |
| Typing the query                                                          | Updated      | Rewritten             | `replace` (M0.2)                                                       |
| Editing a draft that is incomplete or invalid                             | Unchanged    | Unchanged             | None                                                                   |
| Committing a value; add, remove, mode switch, reorder, clear all, reset   | Updated      | Rewritten             | `replace`                                                              |
| Changing the sort                                                         | Updated      | Rewritten             | `replace`                                                              |
| Changing page in a section                                                | That section | Rewritten             | [OI-03](#oi-03--history-entry-for-a-page-change) (proposal: `replace`) |
| Expanding or collapsing the near-compatible section, opening a disclosure | —            | Unchanged (see OI-05) | None                                                                   |
| Opening a vehicle; "‹ Risultati"                                          | Destination  | Destination URL       | `push` (M0.2)                                                          |

Changes to criteria must never add a history entry per change: after any number of criteria and
sort changes, one Back leaves Discovery for the previous page (AC-42, ADR principle 5).

## 12. Empty states, invalid input and missing data

### 12.1 States (FR-31)

| State                                                       | Behaviour                                                                                                                                                                                      |
| ----------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| No criteria, no query                                       | Whole catalogue, price order, as M0.2 (AC-01)                                                                                                                                                  |
| Query with no match                                         | M0.2 empty state ("Nessun veicolo", the query echoed), with the action to clear the query ("Mostra tutti i veicoli" as in M0.2); criteria, if any, are kept and the panel stays usable         |
| Query matches, no compatible, at least one near-compatible  | Compatible section states that no vehicle meets every requirement; near-compatible section expanded (AC-28)                                                                                    |
| Query matches, no compatible and no near-compatible         | One empty state with simple actions: edit the criteria (the panel stays available), "Cancella tutti i criteri", "Ripristina ricerca". No quantitative suggestion, no "nearest" vehicle (AC-30) |
| Compatible present, near-compatible present                 | Near-compatible collapsed, count visible (AC-29)                                                                                                                                               |
| Compatible present, no near-compatible, requirements active | **Proposal:** the near-compatible section is not rendered                                                                                                                                      |
| No preference active                                        | Ranking without `S` (price, name, ID after the near-compatible keys); explanations show only requirements                                                                                      |
| No requirement active                                       | Every candidate compatible; no near-compatible section (§9.4)                                                                                                                                  |
| Ties                                                        | Deterministic tie-breaks down to the ID (AC-33)                                                                                                                                                |
| Priority change                                             | Weights recomputed; `S`, `D`, `V`, membership and order follow; pages back to 1                                                                                                                |
| Values exactly at thresholds                                | §7.10: requirement met at equality; `V = 0.25` admissible; `d = 1` excluded                                                                                                                    |
| Malformed URL                                               | §11.4                                                                                                                                                                                          |
| Sort or page change                                         | §9.2, §9.3                                                                                                                                                                                     |

### 12.2 Invalid and incomplete input (FR-32)

- An editor rejects empty values, non-numbers, `NaN`, infinities, negative values, zero, values
  outside the domain and non-integers where integers are required; it never commits them (§5.5).
- **Proposal for the domains** ([OI-07](#oi-07--input-domains-and-editor-commit-timing)): price an
  integer in euros, 1–1,000,000; seats an integer, 1–9 (the catalogue's maximum); peak DC power an
  integer in kW, 1–1,000; body types a non-empty subset of the five codes. The price editor accepts
  `it-IT` grouping ("40.000") and rejects decimals. The same domains are enforced by the URL
  decoder.

### 12.3 Missing data (FR-33)

| Missing attribute is used by | Effect                                                                    |
| ---------------------------- | ------------------------------------------------------------------------- |
| An active requirement        | Vehicle excluded from both sections (AC-25)                               |
| An active preference         | That satisfaction is 0; the vehicle is not excluded for it (AC-17, AC-25) |
| No active criterion          | No effect on the evaluation (AC-25)                                       |
| The active manual sort key   | Vehicle placed after those that have it, in its section (AC-32)           |

No substitute value is ever invented. Explanations state the missing value (§10.4). In the
current catalogue no evaluated attribute is missing; how tests represent missing data is
[OI-02](#oi-02--test-data-for-missing-attributes-and-pagination).

## 13. Architecture in M0.3

Proportionate to M0.3: pure functions, the URL, local React state. No backend, no store, no
cache, no Web Worker, no new dependency. File names below are proposals (ADR 0001 open question
12); locations are binding in the sense of the layer they belong to.

### 13.1 Layers and modules

| Responsibility                                                                                              | Layer               | Proposed module                                         |
| ----------------------------------------------------------------------------------------------------------- | ------------------- | ------------------------------------------------------- |
| Advanced state types, criterion kinds, values, sort codes, invariants                                       | `src/scenarios/`    | `discoveryScenario.ts`                                  |
| Codec of `q` + `s` + pages: parse with recovery and typed issues, serialise                                 | `src/scenarios/`    | `discoveryScenario.ts` (or `advancedDiscoveryCodec.ts`) |
| Base64URL of ASCII/UTF-8 text with `TextEncoder`/`TextDecoder`, `btoa`/`atob`                               | `src/scenarios/`    | inside the codec (no Node `Buffer`)                     |
| Criteria transitions: add, remove, switch mode, move, clear, reset; draft validation                        | `src/application/`  | `discoveryCriteria.ts`                                  |
| Calibration constants (§7.9) and quantisation (§7.10)                                                       | `src/application/`  | `discoveryCalibration.ts`                               |
| Attribute projection, satisfaction functions, weights, `d`, `D`, `V`, `S`, classification, explanation data | `src/application/`  | `discoveryEvaluation.ts`                                |
| Sections, ranking comparators, manual sorts, pagination                                                     | `src/application/`  | `discoveryResults.ts`                                   |
| Text formatting of reasons and numbers                                                                      | `src/presentation/` | `discoveryFormat.ts`                                    |
| Discovery URLs, origin forwarding, return link                                                              | `src/presentation/` | `routes.ts` (extended)                                  |
| Components: criteria panel, criterion editor, result section, pagination, explanation                       | `src/components/`   | one directory per component, CSS Module each            |
| Route and URL synchronisation                                                                               | `src/app/cerca/`    | `DiscoveryView.tsx` (extended)                          |

Production files stay directly in `src/scenarios/` and `src/application/` so that the ESLint
layer guards of `AGENTS.md` apply; nesting deeper would need a review of the guards.

The evaluation is new application logic. It does not belong to, call or alter the M0.1 charging
engine; no charging mathematics is involved.

### 13.2 Evolution of `SearchScenario` and `OriginContext`

- `SearchScenario` (`{ query }`), `parseSearchScenario` and `SEARCH_QUERY_PARAM` stay as they are:
  the text part of Discovery.
- A new `DiscoveryScenario` composes them:
  `{ search: SearchScenario; advanced: AdvancedDiscoveryState; pages: { compatible: number; near: number } }`,
  with `AdvancedDiscoveryState = { requirements: readonly Criterion[]; preferences: readonly Criterion[]; sort: SortOrder }`.
  The type makes duplicates unrepresentable where practical; otherwise a constructor enforces
  uniqueness, at most four criteria and non-empty body sets, and every transition returns a valid
  state.
- `OriginContext`'s search variant holds a `DiscoveryScenario` instead of a `SearchScenario`.
  `parseOriginContext` keeps its M0.2 rules for `da` and `q` and adds the recovering parse of `s`,
  `pc`, `pq`. Callers (`routes.ts`, `VehicleCard`, `vehicleAnalysis.ts`, `dcSimulatorInteraction.ts`,
  `RicaricaPreview`) change type only. Existing origin tests keep passing; new ones cover the
  extended parameters.

### 13.3 Committed state, drafts and synchronisation

- `DiscoveryView` derives the committed `DiscoveryScenario` from the URL on every render, as M0.2
  does for `q`, and the results from it and the catalogue.
- Drafts live in the editor components. A commit builds the next committed state through the pure
  transitions and rewrites the URL with `history.replaceState` (or the chosen mechanism, §11.6).
- When the URL changes from outside, drafts are dropped (the M0.2 pattern of comparing with the
  last committed value applies).
- Results, sections, explanations and pages are derived, never stored (ADR 0001 Decision 5).

### 13.4 Catalogue and missing attributes

- The evaluation reads a projection: `DiscoveryAttributes = { listPriceEur?: number; seats?: number; bodyType?: BodyType; peakDcPowerKw?: number }`,
  built from a `CatalogueVehicle` by one function in `src/data/` or `src/application/`. Every
  field is optional in the projection so that missing data is representable; for the current
  catalogue every field is present.
- `CatalogueVehicle` and the catalogue data are not changed by M0.3. Unit tests build synthetic
  projections. Fixtures for browser tests are [OI-02](#oi-02--test-data-for-missing-attributes-and-pagination).

### 13.5 Drag-and-drop without a new library

The stack has no sortable-list primitive (Base UI has none). Reordering is implemented with
native pointer events or the HTML drag-and-drop API inside the component, with the keyboard
alternative as a first-class control. If this proves insufficient, the need is reported (ADR 0001
§2); no library is added.

### 13.6 Larger catalogues later

The evaluation is linear in the number of candidates plus a sort; at thousands of vehicles it
remains cheap in the browser. M0.3 adds nothing for that case. What can be deferred: server-side
evaluation, indexing, memoisation (only with a measured need, ADR Decision 5), and catalogue
paging. The projection (§13.4) is the seam a future data source (OpenEV Data) would feed.

### 13.7 ADR 0001 follow-up

M0.3 settles the URL format of Discovery (part of ADR open question 4: encoding, versioning,
partial recovery for this scenario) and confirms that no Redux state is needed. When the
implementation lands, ADR 0001 should be revised to record these as resolved for Discovery; the
comparison scenario's format stays open.

## 14. Non-functional requirements and accessibility

### 14.1 Non-functional

- **NFR-01 Determinism.** The same URL and catalogue always give the same sections, order and
  pages; parsing and serialisation are deterministic. Sorting uses `Intl.Collator`/`localeCompare`
  with `it-IT`; server and client must use the same comparator so that server-rendered and
  hydrated orders agree.
- **NFR-02 Purity and layering.** Evaluation, ranking, transitions and codec are pure TypeScript
  without React, Next.js, Redux or browser-only APIs; ESLint guards pass.
- **NFR-03 No dependency** outside ADR 0001; no change to the stack.
- **NFR-04 Engine unchanged.** No change in `src/domain/` or `src/calculations/`; M0.1 tests
  unchanged and passing.
- **NFR-05 Performance.** Results are recomputed on each committed change without perceptible
  delay on the current catalogue; no cache without a measurement.
- **NFR-06 Robustness.** No URL, input or catalogue content crashes the page.
- **NFR-07 Precision.** Unrounded computation, rounded presentation, boundary rule of §7.10.
- **NFR-08 Visual identity.** Livrea Consolidated as in §10.3; tokens only.

### 14.2 Accessibility (FR-34)

- Every new control is reachable and operable by keyboard in a sensible order, with a visible
  focus indicator and no trap: add, editors, behaviour toggle, remove, move up/down, clear, reset,
  sort, section toggle, pagination, disclosure.
- Reordering by keyboard produces the same state and URL as by pointer (AC-41) and is announced.
- Controls have accessible names that include the criterion they act on ("Sposta su Prezzo",
  "Rimuovi Posti"); the section toggle exposes its expanded state and count; pagination is a
  navigation landmark per section with the current page marked.
- Focus is managed: after adding a criterion, to its editor; after removing one, to a sensible
  neighbour; after a page change, to the section's heading.
- Invalid editor values are announced with the field; the URL recovery notice is a polite status.
- No information by colour alone: violations carry an icon and words; the selected behaviour has
  text.
- Text contrast meets the Livrea Consolidated ratios; `lang="it"` stays.
- A manual accessibility review of the new controls, with at least one screen reader and browser
  combination, is recorded before acceptance (§16).

### 15.3 Mathematical edge cases to cover in unit tests

- Each satisfaction function at its anchors, between anchors, beyond saturation on both sides,
  always within [0, 1]; independence from the catalogue (same inputs, same output, whatever other
  vehicles exist).
- `f_dc` with `t ≤ 50` (zero point at or below 0 kW); `f_seats` with `t = 1`.
- Weights for n = 1–4: values, strict decrease, sum 1 (within floating tolerance).
- `d` at `Δ = 0`, between, `Δ = τ` (d = 1), `Δ > τ` (capped).
- `V` exactly 0.25 (admissible) and just above (excluded); `V` with one and with several
  violations; `V` undefined for compatible vehicles; `D = 0` for compatible vehicles.
- Requirements met at equality (`price = t`, `seats = t`, `peakDc = t`).
- Categorical requirement satisfied together with a numeric violation (near-compatible possible).
- OI-01 scenario documented as a test of the approved rule, whatever its resolution.
- Ties of `S` and `D` produced by different arithmetic paths (quantisation, §7.10).
- No criteria; only preferences; only requirements; four criteria.
- Codec: round trip of every state shape; canonical output; every recovery row of §11.4.

### OI-01 — A second violation can make a vehicle admissible

`V` is the mean severity over the violated requirements only (approved, §7.8). Adding a small
violation lowers the mean, so a vehicle can become admissible by being worse.

Example. Requirements: Prezzo ≤ €40.000 (priority 1, `w = 2/3`), Posti ≥ 5 (priority 2,
`w = 1/3`).

| Vehicle | Price   | Seats | Violations                       | `V`                             | Class           |
| ------- | ------- | ----- | -------------------------------- | ------------------------------- | --------------- |
| X       | €39.000 | 4     | seats `d = 0.5`                  | 0.5                             | Excluded        |
| Y       | €40.800 | 4     | price `d = 0.1`, seats `d = 0.5` | (2/3·0.1 + 1/3·0.5) / 1 ≈ 0.233 | Near-compatible |

Y is worse than X on every criterion and is shown; X is hidden. AC-22 and AC-23 are consistent
with the rule but do not reveal this. Alternatives:

1. **Keep the approved rule.** Simple, matches AC-01–AC-42; the anomaly appears in ordinary use
   whenever a seats violation combines with a small price or DC violation.
2. **Also require each violation to be admissible on its own** (for example `d_i ≤ 0.25` per
   violation, or the single-violation case as a floor). Monotone; changes no current AC
   expectation (AC-21, AC-22, AC-23 still hold) but changes approved behaviour.
3. **Use `D` as well** (rejected by the approved decisions: "Non utilizzare D come condizione
   aggiuntiva").

This specification implements alternative 1 as approved. A product decision should confirm it
or choose another before acceptance.

### OI-02 — Test data for missing attributes and pagination

The current catalogue has 5 vehicles, all with every evaluated attribute, and `CatalogueVehicle`
cannot represent a missing one. AC-32 (E2E part) needs a vehicle without peak DC power; AC-34 needs
more than 20 compatible and more than 20 near-compatible vehicles (at least 42 candidates); the
paging parts of AC-31 and AC-42 need more than 20 in a section. The matrix forbids changing the
visible illustrative catalogue and asks for the adaptation to be stated and reviewed (note 2).

Unit tests are unaffected: they use synthetic projections (§13.4). For browser tests, options:

1. **A fixture catalogue selected at build time** for E2E only (for example an environment
   variable read in `src/data/vehicles.ts`), validated by the same factories, with the visible
   catalogue unchanged. Cost: E2E runs against a build that differs from the shipped one in its
   data; CI needs a second build or a fixture build for E2E; `CatalogueVehicle` must allow a
   missing peak DC power, which also touches Vehicle Analysis and cards.
2. **A page size override for tests** combined with the real catalogue. Does not cover the
   missing-DC case and contradicts the fixed page size of 20.
3. **Downgrade the E2E parts** of AC-32 and AC-34 to Vitest on the result pipeline and keep
   browser checks only for what the real catalogue shows. Changes the matrix's suggested level.

A decision is needed before those E2E tests are written. No option is chosen here.

### OI-03 — History entry for a page change

ADR 0001 Decision 2 covers parameters (`replace`) and navigation between pages or activities
(`push`); a results page is neither explicitly. AC-42 asks for a consistent restore after paging
without fixing the policy. Options: `replace`, consistent with principle 5 and the treatment of
the sort (one Back leaves Discovery); or `push`, the conventional web behaviour (Back returns to
the previous page of results), which would extend the ADR policy. **Proposal:** `replace`.

### OI-04 — What the reset commands reset

- AC-10 says "Ripristina ricerca" presents "l'intero catalogo iniziale", which implies the sort
  returns to "Più pertinenti". The approved text names only query and criteria. **Proposal:** reset
  restores the whole default state (`/cerca`).
- "Cancella tutti i criteri" is specified to remove criteria and keep `q`; the sort is not
  mentioned. **Proposal:** keep the sort, since it is not a criterion.
- Whether a query change returns the pages to 1 (§9.3) is not stated. **Proposal:** yes, since the
  result sets change.

### OI-05 — Expanded state of the near-compatible section

AC-35 restores query, criteria, priorities, sort and pages; the expanded state is not listed, and
ADR Decision 4 does not preserve transient UI. A user who opens a near-compatible vehicle and comes
back would find the section collapsed (when compatible vehicles exist), and scroll restoration
would not reach the card. Options: (1) local state only; (2) an expansion flag in the URL;
(3) expanded whenever `pq > 1`. Continuity (Product Vision §4.5) argues for (2); it adds a
parameter to the URL schema.

### OI-06 — Body type vocabulary

The matrix speaks of "SUV" and "station wagon"; the catalogue has five body types, labelled "SUV
medio", "Station wagon" and others. **Proposal:** the criterion offers exactly the catalogue's five
types with their existing labels, without grouping; "SUV" in AC-14/AC-24 corresponds to
`midSizeSuv`. Grouping (for example all SUV sizes) would be a later taxonomy decision.

### OI-07 — Input domains and editor commit timing

**Proposal:** domains as in §12.2. Commit timing within ADR Decision 2: a valid value is committed
when the user pauses, leaves the field or presses Enter, so that intermediate numbers while typing
("4", "40", "400" on the way to "40000") do not reshuffle the results. Committing on every valid
keystroke (like the query) is the alternative; either satisfies AC-39.

### OI-08 — "UI integration" test level

ADR 0001 §7 approves Vitest for pure logic and Playwright for browser behaviour, and no component
framework. **Proposal:** the matrix's "UI integration" is realised as Vitest on the pure rule plus a
Playwright check of the visible result (§15.1). No framework is added. Reviewers should confirm
the mapping.

### OI-09 — Maintenance plan O6

O6 asks whether M0.3 UI needs the complete Playwright migration or only the ADR decision. Both
are now true (TD-03 decision approved 2026-11-18; migration at parity and legacy script retired,
DEBT-10 resolved 2026-11-24). **Proposal:** record O6 as resolved, with no condition remaining
for M0.3, when this specification is approved.

### OI-10 — Boundary precision

The matrix asks to formalise precision at the boundaries. Proposed in §7.10 (quantisation step
`10⁻⁹`, raw comparison for requirement satisfaction). Listed for review; not a blocker.

### OI-11 — Notice for an invalid `q`

M0.2 opens the default query silently for a repeated or too long `q`. M0.3 requires a notice for an
invalid `s`. Showing the same notice for `q` would change M0.2 behaviour slightly (B). **Proposal:**
show it, for consistency; no M0.2 test asserts its absence.

### OI-12 — Design references for M0.3-specific UI

The wireframes and `02-discovery.svg` cover the panel, criteria tabs, behaviour toggle, cards and
near matches. They do not show the priority handles and their keyboard alternative, the sort list,
pagination per section, the collapsed near-compatible section with its count, the two-level
explanation, or the URL recovery notice. M0.2 let the implementation compose the simulator from
references without a new wireframe cycle. A decision is needed before UI planning: the same
approach (composition by the implementation within §10 and Livrea Consolidated, reviewed at
1440 px), or a short design iteration first.

### OI-13 — Presentation of the ranking numbers

Proposed in §10.5 (two decimals, weights as rounded percent shares). Also: the ranking values
(`S`, `D`, `V`, `f`, `d`) are not M0.1 results, so the ◆ `calcolo` tag, defined as "calculated by
the M0.1 engine", does not apply as defined. **Proposal:** no provenance tag on ranking values;
the vehicle values in the explanation keep their `costruttore` tag.

### OI-14 — Headings without requirements

With no requirement, every candidate is "compatible" by definition. Proposed in §9.4: no
near-compatible section and the M0.2 presentation of the list. Alternatively the section is
always titled "Compatibili". Copy-level; for review.

## 18. Out of scope

- Structured comparison between vehicles; the comparison selection and its UI.
- External catalogues or datasets (OpenEV Data); changes to the illustrative catalogue's content.
- User accounts; saving searches on a server; browser storage of searches.
- Automatic quantitative suggestions to relax requirements; user-editable tolerances ("Rendi
  flessibile").
- New range or trip simulations; estimates (`stima`); trip stops.
- Charging times deduced from peak DC power; the practical "Tempo di ricarica" criterion.
- Criteria other than the four of §5.1 (boot space, daily use, long trips, home charging, ...);
  needs typed into the search field.
- Manual weights or percentages.
- View modes (Schede/Elenco/Differenze), "Ricerche frequenti", "Approfondisci", the "last change"
  notice with undo.
- New Vehicle Analysis or simulator features beyond forwarding the Discovery context.
- M0.2 open question 5 (accent and separator matching).
- Responsive or mobile layouts and dark theme (not designed).
- Architectural refactoring not required here: no backend, no Redux store, no caching layer, no
  change to the M0.1 engine.
- Comprehensive accessibility validation (DEBT-11, pre-release part).
