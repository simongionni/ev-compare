M0.3 turns Discovery from a make-and-model search into a search with criteria: the user can
state requirements and preferences, give them priorities, and see which vehicles meet the
requirements, which come close, and why each result is where it is.

This document turns the approved M0.3 product decisions into a specification. It does not
redesign them. This revision incorporates the decisions approved after the first specification
review (criteria model, numerical objectives, Gaussian preference satisfaction, signed net
distance, dynamic body-type vocabulary and the resolution of OI-01–OI-14); they supersede the
first draft where the two differ. [Appendix A](#appendix-a--changes-from-the-first-draft) lists
what changed. Points that remain undecided are in [§17 Open issues](#17-open-issues) and are not
settled here. Statements marked **Proposal** are technical choices that do not change product
behaviour; they become binding when this specification is approved.

Normative words: **must** is a requirement; **should** is a recommendation an implementation may
depart from with a stated reason; **may** is permitted.

## 1. Goal and rationale

M0.2 proved one end-to-end path (Discovery → Vehicle Analysis → DC simulation) with a direct
search by make or model. Discovery could not yet express needs. M0.3 adds the missing half of
the Discovery activity described in the [user flows](../ux/user-flow-overview.md#discover): text
search and criteria in one continuous loop, with results that explain themselves.

The milestone is deliberately narrow: four attributes whose data the catalogue already holds
(price, seats, body type, peak DC power). It establishes the evaluation model (requirements that
exclude, preferences that order, near matches with bounded tolerances and bounded compensation,
explicit priorities) on a small, verifiable base, so that later criteria (range, charging time,
trips) can be added on the same model without changing its meaning.

## 2. Product Vision alignment

| Product Vision principle                                      | How M0.3 applies it                                                                                                                                 |
| ------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| Complexity available, never mandatory (§1)                    | No criterion is active at first; `/cerca` opens on the whole catalogue as in M0.2. Numeric details of the ranking appear only on request (§10.4).   |
| Direct access, without unnecessary guidance (§3.1)            | No questionnaire, wizard or onboarding. Criteria are added from one command, in any order, while results stay visible.                              |
| Needs before technical specifications (§3.2)                  | Practical criteria (price, seats, body type) and a technical one (peak DC power) coexist in one panel; no mode separates beginners from experts.    |
| Progressive depth (§3.3)                                      | Concrete reasons on each card first; weights, satisfactions and distances behind "Perché questo risultato?".                                        |
| Transparent recommendations (§3.6)                            | Every position is traceable to the user's criteria and the vehicle's data; missing data is stated, never filled in; the score is not a probability. |
| Respect for user autonomy (§3.7)                              | Priorities and targets are the user's, explicit and editable. No automatic suggestion to relax a requirement.                                       |
| Technical accuracy over convenient simplifications (UX §8)    | Peak DC power is presented as a peak specification, never as a charging time or charging performance.                                               |
| Return to the original comparison without losing context (§4) | The whole committed Discovery state lives in the URL and survives opening a vehicle and coming back (§11).                                          |

The [UX Design Principles](../ux/design-principles.md) apply in full, in particular §1, §2 and §6:
no instructional copy for self-evident interactions, no copy written to demonstrate the Product
Vision, no control added only because it is available.

## 5. Criteria model

### 5.1 The four attributes

| Attribute          | Code (proposal) | Kind        | Default mode | Default requirement objective | Default preference objective (proposal, OI-17) | Vehicle attribute                       |
| ------------------ | --------------- | ----------- | ------------ | ----------------------------- | ---------------------------------------------- | --------------------------------------- |
| Prezzo             | `price`         | Numerical   | Requirement  | Maximum                       | Maximum                                        | List price, `listPriceEur`              |
| Posti              | `seats`         | Numerical   | Requirement  | Minimum                       | Exact value                                    | `seats`                                 |
| Carrozzeria        | `body`          | Categorical | Preference   | One or more body types        | One or more body types                         | `bodyType`                              |
| Potenza DC massima | `dc`            | Numerical   | Preference   | Minimum                       | Minimum                                        | Peak DC power, `peakDcPowerKw(vehicle)` |

A **criterion** is one attribute in one mode (requirement or preference) with one objective. Each
attribute can have at most one requirement and at most one preference, independent of each other:
an attribute may therefore appear twice in the active configuration, once in each mode. The
default objective is the operator an editor starts with; it carries no value (§5.7). The input
domains are in [§12.2](#122-invalid-and-incomplete-input-fr-32).

### 5.2 Objectives (FR-35)

- **Numerical objectives.** For price, seats and peak DC power, both requirements and
  preferences support four operators. Each objective explicitly encodes its operator and the
  bound or bounds that apply to it; its **target set** `T` is:

  | Operator    | Bounds            | Target set `T` | Short form (example)  |
  | ----------- | ----------------- | -------------- | --------------------- |
  | Minimum     | `L`               | `x ≥ L`        | "almeno 5 posti"      |
  | Maximum     | `U`               | `x ≤ U`        | "fino a €40.000"      |
  | Exact value | `t`               | `x = t`        | "esattamente 5 posti" |
  | Range       | `L`, `U`, `L < U` | `L ≤ x ≤ U`    | "tra 4 e 7 posti"     |

  All boundaries are inclusive. For an exact objective, `t` is both the lower and the upper
  boundary (`L = U = t`) wherever a formula refers to boundaries. A range requires `L < U`; a range
  with equal bounds is not a valid objective (an exact objective expresses it), so each target set
  has one representation.

- **Categorical objective.** For body type, the objective is a non-empty set `A` of body-type
  codes; the target set is `bodyType ∈ A`. Selected body types are equivalent.

The same objective has the same target set in both modes. In a requirement the target set decides
satisfaction (§6.1); in a preference it is the ideal set of the satisfaction function (§7.4).

### 5.3 Rules (FR-01 to FR-08)

- **FR-01 Initial state.** No criterion is active when Discovery opens without `s`.
- **FR-02 Uniqueness per mode.** Each attribute can have at most one requirement and at most one
  preference. Two criteria on the same attribute in the same mode are prohibited. "Aggiungi
  criterio" offers only attributes that have at least one free mode; with every attribute present
  in both modes it offers none (it may be hidden or disabled, an implementation choice). No state,
  transition or URL can produce a duplicate within a mode.
- **FR-03 Default mode and objective.** A newly added criterion enters its attribute's default
  mode (§5.1) if that mode is free for the attribute, otherwise the other mode. It is placed at the
  end of that mode's priority order and its editor starts with the default objective of that mode.
- **FR-04 Mode switch.** A criterion can move between requirement and preference only when the
  destination mode has no criterion on the same attribute; otherwise the switch is not available.
  The objective (operator and bounds, or body-type set) is kept unchanged; the criterion is placed
  at the end of the new mode's order; the relative order of the others is unchanged in both modes.
  A switch leaves the attribute with one criterion, so it cannot create a conflict (§6.3).
- **FR-05 Reordering.** Within a mode, criteria can be reordered directly (pointer drag) and with
  an equivalent keyboard-operable alternative. Reordering changes priorities and weights, never
  objectives or modes. Reordering across the two modes is not a reorder; it is a mode switch
  (FR-04) through its own control. **Proposal:** dragging is limited to the criterion's own
  section.
- **FR-06 Removal.** Each criterion can be removed individually; the others keep their relative
  order. Removing one of the two criteria on an attribute leaves the other unchanged.
- **FR-07 "Cancella tutti i criteri".** Removes every requirement and preference. It keeps the
  text query and the current sort, returns both sections to page 1 and clears the near-compatible
  expansion (which has no meaning without requirements, §9.4).
- **FR-08 "Ripristina ricerca".** Restores the entire default Discovery state: empty query, no
  criteria, "Più pertinenti", page 1 in both sections, no expansion. The URL becomes `/cerca` and
  the initial catalogue is shown (AC-10).

### 5.4 Priorities

The order of each list is the priority: position 1 is the highest. Requirements and preferences
have separate orders and separate weights (§7.2), also when the same attribute appears in both. The
order is always explicit in the interface; weights are never edited directly (no percentages to
type).

### 5.5 Text search and criteria (FR-09)

The text query is applied first, with the M0.2 rules: the candidate set is the catalogue vehicles
whose name matches `q`. Criteria are evaluated only on the candidates. The query is not a
criterion: it has no mode, priority or weight and is not part of `s`.

### 5.6 Body-type vocabulary (FR-37)

- The selectable body types are the distinct body-type codes of the vehicles in the catalogue
  available at evaluation time: the whole catalogue in use, not the candidates matching `q` and not
  the vehicles left by the applied criteria.
- A body type introduced by a future catalogue becomes selectable without any change to the
  criterion, its evaluation or its codec. No part of the specification, the types or the URL schema
  limits the vocabulary to the five current codes.
- Codes are stable identifiers, separate from UI labels. Serialised state stores codes only; a
  label change never breaks a link. Every selectable code must have an Italian label; where labels
  are defined and what happens to a code without one is [OI-16](#oi-16--body-type-labels-for-catalogue-defined-codes).
- **Proposal:** options are listed in label order (`it-IT` collation), then by code.
- A code referenced by a URL but absent from the current vocabulary is handled by URL recovery
  (§11.4): it is dropped, and a non-blocking notice is shown because the configuration changed.
- **Proposal for the identifier syntax:** an ASCII letter followed by ASCII letters and digits, at
  most 32 characters (`/^[A-Za-z][A-Za-z0-9]{0,31}$/`), validated by the catalogue factory. The
  current codes satisfy it.

### 5.7 Committed state and drafts (FR-10)

The **committed** Discovery state is the one the URL represents (ADR 0001 Decision 2, principle
1). Editors work on a **draft**, which is local React state:

- A criterion just added, without a valid objective, is a draft. It is visible in its section but
  is not committed, does not take part in the evaluation, does not count in the weights and is not
  in the URL. There are no default values for criteria: the product does not choose a budget, a
  number of seats, a body type or a power on the user's behalf.
- A draft is **valid** when its operator and every bound it needs are present and in the domain
  (§12.2), a range has `L < U`, a body-type set is non-empty, and, if the attribute also has a
  criterion in the other mode, the two target sets intersect (§6.3). Validation runs during
  editing; the editor shows at once that a value is not valid and why.
- While a draft is incomplete or invalid, the committed criterion, the results and the URL stay
  unchanged (AC-39, AC-46, AC-48). No intermediate invalid state is ever committed.
- A valid draft is committed after a short pause in editing, when the field loses focus, or when
  the user presses Enter, whichever comes first (decided, OI-07). Intermediate values typed without
  a pause ("4", "40", "400" on the way to "40000") are not committed. **Proposal:** a pause of
  500 ms, defined with the calibration (§7.9). Selecting a body type or an operator is a discrete
  choice and is committed at once when the resulting draft is valid. No mandatory confirmation
  button is introduced (ADR 0001 Decision 2).
- Drafts are transient UI: they are not preserved across navigation (ADR 0001 Decision 4). When
  the URL changes from outside (Back, Forward, a link), drafts are discarded and the editors show
  the committed state.
- Add, remove, mode switch, reorder, clear and reset act on the committed state at once when they
  concern committed criteria. A mode switch or reorder of a draft only changes the draft.

## 6. Requirement and preference semantics

### 6.1 Requirements (FR-11)

A requirement is satisfied when the vehicle's attribute lies in the requirement's target set
(§5.2): `x ≥ L` for a minimum, `x ≤ U` for a maximum, `x = t` for an exact value, `L ≤ x ≤ U` for a
range, `bodyType ∈ A` for body type. Boundaries are inclusive. A requirement whose attribute is
missing is not evaluable (§12.3).

A preference never excludes; it measures how close the vehicle is to its ideal set (§7.4, §7.6).

### 6.2 Combination (FR-12)

- Several body types in one criterion are combined with **OR**.
- Different requirements are combined with **AND**: a vehicle is compatible only if it satisfies
  all of them.
- **Preferences never exclude a vehicle**, whatever their satisfaction (AC-18). They only order.
- Requirement priorities **do not make a requirement optional**. They weigh the net distance of
  near matches (§7.8) and nothing else.
- A requirement and a preference on the same attribute are evaluated independently: the
  requirement only through §6.1, §7.7 and §7.8, the preference only through §7.3–§7.6.

### 6.3 Compatibility between a requirement and a preference (FR-36)

When an attribute has both a requirement and a preference, their declared target sets must
intersect over the attribute's domain `X_a`:

```text
T_req ∩ T_pref ∩ X_a ≠ ∅
```

- Numerical: write each target set as an interval `[lo, hi]`, with a missing lower bound read as
  `−∞` and a missing upper bound as `+∞`. The intersection is `[max(lo_req, lo_pref),
min(hi_req, hi_pref)]`, intersected with `X_a`. For price and peak DC power, `X_a` is the
  positive real numbers and the intersection is non-empty when `max(lo) ≤ min(hi)`. For seats, `X_a`
  is the integers from 1 to `MAX_SEATS`, and the intersection is non-empty when it contains an
  integer of that range: `max(⌈max(lo)⌉, 1) ≤ min(⌊min(hi)⌋, MAX_SEATS)`.
- Categorical: `A_req ∩ A_pref ≠ ∅`.
- Touching boundaries intersect: a maximum €40.000 and a minimum €40.000 share €40.000.
- The check uses only the declared target sets, never satisfaction values or vehicle data.

Examples (approved): price ≤ €40.000 with a preference of exactly €45.000 is invalid; price
≤ €40.000 with a preference of €35.000–€45.000 is valid; seats 4–7 with a preference of exactly 5
is valid; seats ≥ 5 with a preference of ≤ 4 is invalid. Test cases are AC-44 and AC-45.

An incompatible configuration can never be committed:

- In an editor, a draft that would conflict with the attribute's criterion in the other mode is
  invalid (§5.7). The editor explains the conflict in context, naming the other criterion and its
  objective (for example "Non compatibile con il requisito Prezzo: fino a €40.000"; exact copy is
  an implementation choice). This applies whichever of the two criteria is being edited.
- In a URL, a conflicting pair is recovered by keeping the requirement and dropping the
  preference, with a notice (§11.4).

### 6.4 Peak DC power

The criterion is the manufacturer-type peak DC power already shown on the card ("Potenza DC
massima", `costruttore`). The interface must not describe it as a charging time, a charging
speed in practice or a session outcome, and must not derive one from it (UX principle 8; the
wireframe README's distinction between the technical filter and the practical charging-time
criterion). The charging-time criterion is out of scope (§18).

## 7. Evaluation engine: formulas and parameters

All values are computed unrounded; only presentation rounds (§10.5). Comparisons at decision
boundaries follow §7.10.

### 7.1 Notation

The same symbol has the same meaning throughout this document and the acceptance matrix.

| Symbol             | Meaning                                                                                             |
| ------------------ | --------------------------------------------------------------------------------------------------- |
| `v`, `x`           | A candidate vehicle; `x` is the value of the attribute a criterion refers to                        |
| `L`, `U`, `t`      | Lower bound, upper bound, exact value of a numerical objective; for an exact objective `L = U = t`  |
| `T`, `I`           | Target set of an objective; `I` is the same set when it is a preference's **ideal set**             |
| `A`                | Set of body-type codes of a categorical objective                                                   |
| `i`, `w_i`         | A committed requirement and its weight                                                              |
| `j`, `p_j`         | A committed preference and its weight                                                               |
| `δ_j(x)`           | Distance of `x` from the ideal set `I` of preference `j` (§7.4)                                     |
| `σ⁻`, `σ⁺`         | Gaussian scales of a preference, below and above its ideal set (§7.5)                               |
| `f_j(v)`           | Satisfaction of preference `j`, in `[0, 1]` (§7.4, §7.6)                                            |
| `S(v)`             | Preference score (§7.3)                                                                             |
| `Δ_i(x)`           | Unfavourable distance of `x` from the target set of requirement `i` (§7.7)                          |
| `τ⁻`, `τ⁺`         | Requirement tolerances, below the lower and above the upper boundary (§7.7)                         |
| `d_i(v)`           | Normalised violation of requirement `i`, in `[0, 1]` (§7.7)                                         |
| `φ_i(x)`, `κ_i`    | Favourable deviation of a satisfied, credit-eligible requirement and its saturation distance (§7.8) |
| `λ`, `c_i(v)`      | Maximum credit per eligible requirement, and the credit of requirement `i`, in `[0, λ]` (§7.8)      |
| `g_i(v)`           | Signed contribution of requirement `i` (§7.8)                                                       |
| `D_net(v)`         | Net weighted distance (§7.8)                                                                        |
| `B(v)`, `\|B(v)\|` | Set of requirements `v` violates, and its size                                                      |
| `θ`                | Admissibility threshold on `D_net` (§7.9)                                                           |

`σ` (preference scales) and `τ` (requirement tolerances) are different parameters with different
roles. They must not be mixed, even where their values coincide.

### 7.2 Weights (FR-13)

For a list (requirements or preferences) of `n ≥ 1` committed criteria, the criterion at position
`k` (1-based) has weight

```text
weight_k = (n − k + 1) / (n(n + 1) / 2)
```

Requirement weights are written `w_i`, preference weights `p_j`. The weights of a list are
positive, strictly decreasing with the position and sum to 1. The two lists are weighted
independently; requirement weights are normalised over **all** committed requirements, satisfied
or violated. Each list holds at most one criterion per attribute, so `n ≤ 4`:

| n   | Weights (position 1 → n) |
| --- | ------------------------ |
| 1   | 1                        |
| 2   | 2/3, 1/3                 |
| 3   | 3/6, 2/6, 1/6            |
| 4   | 4/10, 3/10, 2/10, 1/10   |

Weights are not configurable in M0.3.

### 7.3 Preference score (FR-14)

```text
S(v) = Σ_j p_j · f_j(v)        over the committed preferences j
```

Each satisfaction function `f_j` returns a value in `[0, 1]`. It depends only on the vehicle's
attribute and the preference's objective: it is independent of the weight, of the other criteria
(including a requirement on the same attribute) and of the catalogue. `S(v)` is in `[0, 1]`. With
no committed preference, `S` is undefined: it is not shown and is skipped in the ranking (§9.1).

`S` is a ranking score derived from the user's stated preferences. It must not be presented as a
probability, a percentage of compatibility or an objective measure of suitability.

### 7.4 Numerical preference satisfaction: generalised Gaussian

For a numerical preference with ideal set `I` (its target set, §5.2), the distance from the ideal
set is

```text
δ(x, I) = L − x     if a lower bound applies and x < L
          x − U     if an upper bound applies and x > U
          0         otherwise (x ∈ I)
```

For a minimum only the lower bound applies, for a maximum only the upper bound; for an exact value
both, with `L = U = t`; for a range both. The scale is side-specific: `σ = σ⁻` when `x < L`,
`σ = σ⁺` when `x > U` (§7.5). The satisfaction is

```text
f(x) = exp( −4 · ln 2 · (δ(x, I) / σ)² )        equivalently  2^( −4 · (δ / σ)² )
```

Properties (verified by AC-51):

- `f(x) = 1` throughout the ideal set, and `0 < f(x) < 1` outside it, mathematically.
- `f = 0.5` at distance `σ/2` and `f = 0.0625` at distance `σ`.
- `f` is continuous everywhere, including at the boundaries of `I` (where `δ = 0` on both sides),
  and strictly decreasing in `δ` outside `I`.
- `f` approaches 0 asymptotically. No truncation threshold is applied; a result that underflows to
  0 in floating point for very large distances is acceptable.
- Shape: a Gaussian peak for an exact value; a plateau with Gaussian sides for a range; a plateau
  extending in the accepted direction with one Gaussian side for a minimum or a maximum.

This function replaces the first draft's piecewise-linear functions and their anchors (70 % at the
price threshold, 60 % at the DC threshold, exact zeros at fixed distances), which are superseded.

### 7.5 Gaussian scales

| Attribute     | `σ⁻` (below the ideal set)      | `σ⁺` (above the ideal set)      |
| ------------- | ------------------------------- | ------------------------------- |
| Price         | `0.20 · L` (the lower boundary) | `0.20 · U` (the upper boundary) |
| Seats         | 1 seat                          | 2 seats                         |
| Peak DC power | 50 kW                           | 50 kW                           |

For an exact price objective, `σ⁻ = σ⁺ = 0.20 · t`. The seats asymmetry is intentional: one
missing seat is penalised more strongly than one extra seat. These scales belong to the preference
satisfaction function only; they are not requirement tolerances (§7.7).

### 7.6 Body-type preference satisfaction

Categorical: `f = 1` if the vehicle's body type is in the selected set `A`, `f = 0` otherwise. All
selected types have equal satisfaction; there is no similarity between types and no categorical
similarity matrix. A missing body type gives `f = 0` (§12.3).

### 7.7 Requirement distances (FR-15)

For a numerical requirement, the unfavourable distance from the applicable boundary is

```text
Δ_i(x) = L − x     if a lower bound applies and x < L
         0         if x is in the target set
         x − U     if an upper bound applies and x > U
```

For one-sided objectives only the relevant boundary applies; an exact objective uses `L = U = t`.
The distance is normalised by the side-specific tolerance (`τ = τ⁻` when `x < L`, `τ = τ⁺` when
`x > U`):

```text
d_i(x) = min(1, Δ_i(x) / τ)
```

| Attribute     | `τ⁻` (below the lower boundary) | `τ⁺` (above the upper boundary) |
| ------------- | ------------------------------- | ------------------------------- |
| Price         | `0.20 · L`                      | `0.20 · U`                      |
| Seats         | 2 seats                         | 2 seats                         |
| Peak DC power | 50 kW                           | 50 kW                           |

A satisfied requirement has `d_i = 0`. A violated numerical requirement has `0 < d_i ≤ 1`; it can
only qualify for near compatibility if `d_i < 1` (§8.2). Body type as a requirement has no
distance: it is satisfied or violated, and a violation excludes the vehicle.

### 7.8 Favourable credits and net weighted distance (FR-16)

Two kinds of satisfied requirement earn a bounded **favourable credit**:

| Eligible requirement | Favourable deviation `φ_i(x)` | Saturation `κ_i` |
| -------------------- | ----------------------------- | ---------------- |
| Price, maximum `U`   | `max(0, U − x)`               | `0.20 · U`       |
| Peak DC, minimum `L` | `max(0, x − L)`               | 100 kW           |

```text
c_i(v) = λ · min(1, φ_i(x) / κ_i)        λ = 0.25
```

The credit grows linearly with the favourable deviation, is 0 at the boundary and saturates at
`λ` from `κ_i` onwards. No other requirement earns a credit: not seats, not body type, not exact
objectives, not ranges, and not opposite-direction objectives (a minimum price or a maximum DC
power). The Gaussian satisfaction model is not used to calculate credits.

Each requirement contributes a signed value:

```text
g_i(v) =  d_i(v)     if i is a violated numerical requirement
         −c_i(v)     if i is satisfied and eligible for a credit
          0          if i is satisfied and not eligible
```

and the **net weighted distance** is

```text
D_net(v) = Σ_i w_i · g_i(v)        over all committed requirements i
```

`D_net` is defined for a vehicle on which every committed requirement is evaluable and no
categorical requirement is violated; otherwise the vehicle is excluded before `D_net` is
considered (§8.2). Because the weights are normalised over all requirements, a satisfied
requirement contributes 0 (or a credit) but still lowers the share of the others: this is
intentional and approved.

`D_net` replaces the first draft's overall distance `D` and mean violation severity `V`; neither
remains, explicitly or implicitly, in the classification or the ranking.

### 7.9 Calibration parameters (FR-17)

Approved as the initial calibration, except where marked as a proposal. They must be defined in
one module, named, documented next to their definition and covered by tests, so that a later
recalibration is one change.

| Parameter                                              | Value                                    |
| ------------------------------------------------------ | ---------------------------------------- |
| Gaussian exponent constant                             | `4 · ln 2` (fixes `f = 0.5` at `σ/2`)    |
| Price preference scales `σ⁻`, `σ⁺`                     | `0.20 · L`, `0.20 · U`                   |
| Seats preference scales `σ⁻`, `σ⁺`                     | 1 seat, 2 seats                          |
| DC preference scales `σ⁻`, `σ⁺`                        | 50 kW, 50 kW                             |
| Price requirement tolerances `τ⁻`, `τ⁺`                | `0.20 · L`, `0.20 · U`                   |
| Seats requirement tolerances `τ⁻`, `τ⁺`                | 2 seats, 2 seats                         |
| DC requirement tolerances `τ⁻`, `τ⁺`                   | 50 kW, 50 kW                             |
| Maximum credit per eligible requirement `λ`            | 0.25                                     |
| Price credit saturation `κ_price` (maximum-price only) | `0.20 · U`                               |
| DC credit saturation `κ_dc` (minimum-DC only)          | 100 kW                                   |
| Admissibility threshold `θ`                            | `D_net ≤ 0.25`                           |
| Page size per section                                  | 20                                       |
| Quantisation step `ε` (§7.10)                          | `10⁻⁹` (proposal, retained after review) |
| Editor commit pause (§5.7)                             | 500 ms (proposal)                        |

`λ` and `θ` have the same value but are distinct parameters.

### 7.10 Numerical precision at boundaries (FR-18)

Decided (OI-10): computations use unrounded values; comparisons are deterministic; rounding is
presentation only. The first draft's quantisation proposal was reviewed against the revised model
and is retained:

- Requirement satisfaction compares the raw attribute with the raw bounds (`x ≥ L`, `x ≤ U`,
  `x = t`); the requirement–preference intersection (§6.3) compares raw integer bounds. Bounds are
  integers (§12.2); vehicle attributes are compared as stored, without rounding.
- Derived values used in decisions or ranking (`d_i` against 1, `D_net` against `θ`, `S` and
  `D_net` as ranking keys) are compared after quantisation to the fixed step `ε = 10⁻⁹`
  (`round(x / ε)`), defined once with the calibration. Quantising, rather than comparing with a
  tolerance, keeps the sort comparators transitive. Intermediate values (`δ`, `f_j`, `Δ_i`, `d_i`,
  `c_i`, `g_i`) are not quantised before aggregation.
- A value mathematically equal to a threshold is therefore on the threshold: `D_net = 0.25` is
  admissible and `d_i = 1` is not, whatever arithmetic path produced them (AC-21, AC-61).
- Consequence for the Gaussian model, stated so that reviewers expect it: quantisation does not
  truncate `f` (it stays unrounded in `S` and in explanations), but two scores that differ by less
  than `10⁻⁹` are equal ranking keys and are ordered by the next key. This only occurs when every
  preference is far from its ideal set (beyond about `2.7 σ`), where such differences carry no
  meaning.
- Displayed values are rounded separately (§10.5) and never feed back into decisions.

### 7.11 Mathematical properties

The model must satisfy, and tests must demonstrate (AC identifiers in the matrix):

1. **Bounds.** `f_j ∈ [0, 1]`, `S ∈ [0, 1]`, `d_i ∈ [0, 1]`, `c_i ∈ [0, λ]`. For a
   near-compatible vehicle `−λ < D_net ≤ θ`.
2. **Signed contributions.** `g_i > 0` only for violated numerical requirements, `g_i < 0` only
   for satisfied eligible requirements with `φ_i > 0`, and `g_i = 0` otherwise.
3. **Continuity.** For a maximum-price requirement `g_i` is a continuous, non-decreasing function
   of the price: `−λ` up to `0.8 U`, rising linearly to 0 at `U`, then to 1 at `1.2 U`. For a
   minimum-DC requirement it is the mirror image in peak DC power, saturating 100 kW above `L`.
   Other numerical requirements have `g_i = 0` in the target set and `d_i` outside it.
4. **Monotonicity.** With fixed objectives and priorities, an unfavourable change of a vehicle's
   attribute (a higher value for a maximum objective, a lower value for a minimum objective, a
   larger `Δ_i` for an exact or range objective) never decreases `g_i`, `D_net` or `|B(v)|`, and
   never makes an excluded vehicle near-compatible or a near-compatible vehicle compatible. The
   first draft's counterexample (OI-01) is a regression test of this property (AC-59).
5. **No compensation of exclusions.** No credit can admit a vehicle that violates a categorical
   requirement, lacks data for a requirement, or has `d_i = 1` on any requirement (AC-58, AC-60).
6. **Weighting over all requirements.** Adding or reordering requirements changes the weights and
   therefore `D_net`; adding a satisfied requirement can make an excluded vehicle near-compatible.
   This is intended; monotonicity (property 4) is claimed only for fixed criteria (AC-22, AC-26).
7. **Independence.** `f_j` does not depend on its weight, on other criteria or on the catalogue;
   preferences never affect classification (AC-18, AC-54).

## 8. Compatibility and near compatibility

### 8.1 Pipeline (FR-19)

1. Candidates: the catalogue vehicles matching `q` (§5.5).
2. Each candidate is classified as **compatible**, **near-compatible** or **excluded** (§8.2).
3. Compatible and near-compatible vehicles are shown in two separate sections; excluded vehicles
   are not shown and there is no "non valutabili" section. With no requirement committed, every
   candidate is compatible and is shown in one list (§9.4).
4. Each section is ordered (§9) and paginated (§9.3).

A vehicle belongs to exactly one class; no vehicle appears in both sections.

### 8.2 Classification (FR-20)

For a candidate `v` and the committed requirements, in this order:

1. If any attribute needed by a committed requirement is missing → **excluded**.
2. If `v` violates no requirement → **compatible**. With no requirement committed, every
   candidate is compatible.
3. If `v` violates a body-type requirement → **excluded**.
4. If any violated numerical requirement has `d_i ≥ 1` → **excluded**.
5. If `D_net(v) ≤ θ` (0.25) → **near-compatible**; otherwise → **excluded**.

Equivalently, a vehicle is near-compatible exactly when it violates at least one requirement,
every committed requirement is evaluable, no categorical requirement is violated, every violated
numerical requirement has `d_i < 1`, and `D_net ≤ 0.25`. No other condition applies.

Preferences never take part in the classification (AC-18; AC-26: reordering preferences never
changes membership). Reordering requirements changes their weights and therefore `D_net`, so it
can change which vehicles are near-compatible (AC-26).

Consequences of the approved rule, stated so that tests and reviewers expect them:

- A vehicle that is worse than another on every requirement can never be admitted when the better
  one is excluded (§7.11 property 4). The first draft's anomaly (OI-01) no longer exists.
- A single seats violation (`d = 0.5` for one missing seat) is near-compatible or excluded
  depending on its weight and on the other requirements' contributions; it is no longer always
  excluded (AC-22 is revised accordingly).
- Large credits on high-priority requirements can admit a sizeable violation of a low-priority
  requirement, up to just below its tolerance (AC-57). The individual tolerance `d_i < 1` remains
  the bound on any single violation.

## 9. Ranking, manual sorting and pagination

### 9.1 "Più pertinenti" (default) (FR-21)

Compatible section (or the single list without requirements), keys in order:

1. `S` decreasing (skipped when no preference is committed);
2. list price increasing;
3. vehicle name (`make model`) increasing, `it-IT` collation;
4. vehicle ID increasing (code-unit order).

With no preference committed this is the M0.2 order (price, name, ID), so `/cerca` without
criteria satisfies AC-01. `D_net` and credits play no part in ordering compatible vehicles.

Near-compatible section, keys in order:

1. number of violated requirements `|B(v)|` increasing;
2. `D_net` increasing;
3. `S` decreasing (skipped when no preference is committed);
4. list price increasing;
5. name increasing;
6. ID increasing.

### 9.2 Manual sort orders (FR-22)

| Sort (label)             | Code (proposal) | Keys after the main one    |
| ------------------------ | --------------- | -------------------------- |
| Più pertinenti (default) | `rel`           | §9.1                       |
| Prezzo crescente         | `price-asc`     | name, ID                   |
| Prezzo decrescente       | `price-desc`    | name, ID                   |
| Potenza DC decrescente   | `dc-desc`       | price increasing, name, ID |
| Marca e modello A–Z      | `name`          | price increasing, ID       |

Rules:

- A manual sort orders each section separately; it never moves a vehicle between sections.
- Tie-breaks are price increasing, name, ID, omitting the key already used as the main key.
- A vehicle missing the attribute of a sort key goes after every vehicle that has it, within its
  section, for that key (AC-32); among themselves such vehicles are ordered by the following keys.
- Changing the sort returns both sections to page 1 (AC-31).

### 9.3 Pagination (FR-23)

- 20 vehicles per page, per section; the two sections are paginated independently (AC-34).
- The current page of each section is in the URL (§11.2).
- Changing the query, any committed criterion (add, remove, objective, mode, order, clear, reset)
  or the sort returns both sections to page 1 (decided, OI-04; AC-64). Expanding or collapsing the
  near-compatible section does not change the pages.
- Explicit navigation to another page of a section creates a history entry (`push`, §11.6).
- A page beyond the last existing page shows the last page (the catalogue may have changed since
  the link was made, AC-36).
- **Proposal:** pagination controls appear only for a section with more than 20 vehicles.

### 9.4 Section presentation (FR-24)

- **No requirement committed** (with or without preferences): every candidate is shown in one
  list, with the M0.2 presentation (count and results), without a "Compatibili" heading and
  without a near-compatible section (decided, OI-14; AC-65). Its page is `pc`; `pq` and the
  expansion flag have no effect.
- **Requirements committed**: the "Compatibili" section, then the "Quasi compatibili" section.
- The expansion of the near-compatible section is part of the committed state and of the URL
  (decided, OI-05; flag `x`, §11.3), so that returning from Vehicle Analysis restores it (AC-62).
  Its effective presentation is deterministic (AC-63):

  | Compatible | Near-compatible | Effective presentation of the near-compatible section                      |
  | ---------- | --------------- | -------------------------------------------------------------------------- |
  | ≥ 1        | ≥ 1             | Expanded if `x` is set, otherwise collapsed with its count visible (AC-29) |
  | 0          | ≥ 1             | Expanded automatically, whatever `x` says (AC-28)                          |
  | ≥ 1        | 0               | Not rendered (**Proposal**)                                                |
  | 0          | 0               | Empty state (§12.1, AC-30)                                                 |

  Automatic expansion takes precedence over the flag. It does not rewrite the flag: `x` depends
  only on the user's action, not on the results, so the canonical URL does not depend on the
  catalogue. **Proposal:** while expansion is automatic the section toggle is not offered, since
  the section is the only result list.

- The flag is set and cleared only by the section toggle (`replace`, §11.6). **Proposal:** it is
  kept across query, criteria and sort changes. "Cancella tutti i criteri" and "Ripristina ricerca"
  clear it (FR-07, FR-08); it is also dropped from the canonical state whenever no requirement is
  committed.

### 10.4 Explanations (FR-25)

Two levels (AC-40), progressive (decided, OI-13):

**Level 1, on every card, always visible: concrete reasons.** Short statements built from the
vehicle's values and the user's criteria, never from scores:

- For a near-compatible vehicle, every violated requirement with the vehicle's value and the gap
  (wireframe: "REQUISITO NON RISPETTATO · Budget: €46.800: €1.800 oltre il limite"; similarly
  "2.000 € sotto il minimo", "6 posti invece di 5").
- For a compatible vehicle, the criteria it meets, with the vehicle's value, compactly; the
  preferences that most contributed may be named.
- A missing attribute is stated as not available ("Potenza DC non disponibile"), never replaced by
  a value or hidden.

**Level 2, on request, "Perché questo risultato?":** a disclosure on the card showing, per
committed criterion: the vehicle's value (with its provenance tag), the objective, the mode and
position, and

- for a preference: satisfaction `f_j`, weight `p_j`, contribution `p_j · f_j`, and the total `S`;
- for a requirement: met or violated; for a violated numerical requirement `d_i`; for a satisfied
  eligible requirement of a near-compatible vehicle its credit `c_i`; the weight `w_i` and the
  contribution `w_i · g_i`; for a near-compatible vehicle also `D_net` and the number of
  violations, which determine its position.

`S` and `D_net` are labelled as ranking values derived from the user's criteria. They are never
presented as a probability, a likelihood or a percentage of compatibility. The ◆ `calcolo` tag
belongs to M0.1 charging calculations and is not used for any ranking value; the vehicle values
in the explanation keep their `costruttore` tag.

The disclosure is a button with an expanded state; its content is text, reachable by keyboard and
screen readers. It is transient UI (not preserved on navigation).

### 10.5 Number presentation

**Proposal:** `it-IT` formatting; satisfactions, distances, credits, `S` and `D_net` with two
decimals ("0,85", "−0,13"), with a value that is not exactly 0 or 1 but would round to it written
"< 0,01" or "> 0,99", so that rounding never suggests a vehicle is inside or outside an ideal set;
weights as shares of the list's total, rounded to whole percent ("50%"), explicitly labelled as
weights. The score is never written as a percentage. Prices and power use the M0.2 formats.

### 10.6 Feedback

- The results header is a polite live region, as in M0.2: committed changes announce the new
  counts.
- A reorder announces the criterion's new position.
- No "effect of the last change" notice and no undo (wireframe elements out of scope).

## 11. URL, navigation and context

### 11.1 Ownership

The committed Discovery state is owned by the URL (ADR 0001 Decision 1). It is rebuilt from the
URL alone, with no storage, history state or store. Drafts, open editors, disclosure state and
hover are local and transient. The near-compatible expansion is committed state (§9.4). **No Redux
store is introduced**: M0.3 has no shared state that the URL or a component does not already own.

### 11.2 Parameters (FR-26)

| Parameter | Meaning                                                                       | Default (omitted) | Validation                                       |
| --------- | ----------------------------------------------------------------------------- | ----------------- | ------------------------------------------------ |
| `q`       | Text query, as in M0.2                                                        | empty             | M0.2 rules (single, ≤ 100 characters after trim) |
| `s`       | Advanced state: criteria, objectives, modes, priorities, sort, expansion flag | default state     | §11.3, §11.4                                     |
| `pc`      | Page of the compatible section, or of the single list (proposal name)         | 1                 | single positive integer, canonical decimal       |
| `pq`      | Page of the near-compatible section (proposal name)                           | 1                 | single positive integer, canonical decimal       |

Canonical serialisation: parameters in the order `q`, `s`, `pc`, `pq`; each omitted when at its
default; `pq` also omitted when no requirement is committed. `/cerca` is therefore the M0.2
initial URL, and `/cerca?q=…` the M0.2 search URL. Unknown parameters are ignored. The parameter
names `pc` and `pq` are a proposal; `q` and `s` are approved.

### 11.3 Encoding of `s` (FR-27)

Approved: canonical JSON, explicit version, Base64URL, no compression, deterministic. Version 1
has not been released; this revision redefines it without any compatibility obligation towards
the first draft's unimplemented format.

**Proposal for version 1:**

```text
s = base64url( utf8( canonical JSON ) )        RFC 4648 §5 alphabet, no padding

State      = { "v": 1, "r": [Criterion…], "p": [Criterion…], "o": Sort, "x": 1 }

Criterion  = { "k": Numeric, "op": "min",   "lo": <integer> }
           | { "k": Numeric, "op": "max",   "hi": <integer> }
           | { "k": Numeric, "op": "eq",    "t":  <integer> }
           | { "k": Numeric, "op": "range", "lo": <integer>, "hi": <integer> }    lo < hi
           | { "k": "body",  "in": [<body type code>, …] }                         non-empty

Numeric    = "price" | "seats" | "dc"
Sort       = "price-asc" | "price-desc" | "dc-desc" | "name"
```

- `r` is the requirements list, `p` the preferences list; array order is the priority. Mode is
  given by the list, so a mode switch moves the entry unchanged (FR-04). Each list contains at most
  one entry per `k`; the same `k` may appear once in `r` and once in `p`.
- Each numerical criterion carries its operator `op` and exactly the bounds that operator needs:
  `lo` for `min`, `hi` for `max`, `t` for `eq`, `lo` and `hi` for `range`.
- Body type codes are the catalogue's stable codes (§5.6), never UI labels, and are not limited to
  a fixed list.
- `x: 1` records that the user expanded the near-compatible section (§9.4). It is the only value
  of `x`; collapsed is the absence of `x`.
- Canonical form: keys in the order shown (`v`, `r`, `p`, `o`, `x`; `k`, `op`, `lo`, `hi`, `t`;
  `k`, `in`); no whitespace; integers without sign, fraction, exponent or leading zeros; body type
  codes without duplicates, in code-unit order; `r`, `p` omitted when empty; `o` omitted for `rel`;
  `x` omitted when not set or when `r` is empty. The default state (no criteria, `rel`, no
  expansion) has no `s` at all.
- The decoder accepts any JSON that satisfies the schema (other key orders, whitespace, optional
  padding, numbers such as `4e4` that denote an integer); the encoder always writes the canonical
  form. Parsing a serialised state yields an equal state (round trip, ADR 0001 Decision 1).
- `s` contains no free text (the query stays in `q`); with the identifier syntax of §5.6 its JSON is
  ASCII.
- An `s` longer than 4,096 characters is treated as undecodable (a guard against abuse; a valid
  state with a large vocabulary stays well below it).
- The decoder takes the current body-type vocabulary as an input, so that it can recover unknown
  codes (§11.4) without depending on the catalogue module.

**Evolution.** `v` identifies the schema. Additive optional fields may be added within a version:
the v1 decoder ignores unknown keys at the top level and in criteria. An incompatible change
introduces `v: 2`; the decoder then keeps accepting v1 and maps it to the new model, so released
links keep working. A version the decoder does not know is undecodable (§11.4).

### 11.4 Invalid URLs and partial recovery (FR-28)

Parsing never fails the page. It returns the recovered state and a list of typed issues
(errors as values). `q`, `s`, `pc` and `pq` are parsed independently: an invalid `s` never loses
a valid `q` (AC-38), and the reverse (AC-67). Recovery steps apply in the order of the table; the
result always satisfies every invariant of §5–§6.

| Case                                                                                           | Result                                                                                            | Notice |
| ---------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- | ------ |
| `s` repeated, too long, not Base64URL, not UTF-8, not JSON, not an object, `v` missing/unknown | Default advanced state (no criteria, `rel`, no expansion)                                         | Yes    |
| `r` or `p` not an array                                                                        | That list treated as empty                                                                        | Yes    |
| A criterion malformed: not an object, unknown `k`, unknown `op`                                | That criterion dropped; the others kept in their order (AC-37)                                    | Yes    |
| A numerical criterion with a required bound missing, not an integer, or outside the domain     | That criterion dropped                                                                            | Yes    |
| A numerical criterion with a bound key its operator does not use (`hi` with `min`, …)          | That criterion dropped (the objective is ambiguous)                                               | Yes    |
| A range with `lo ≥ hi`                                                                         | That criterion dropped                                                                            | Yes    |
| `in` not an array, or with entries that are not well-formed codes                              | Malformed entries dropped; criterion dropped if none remains                                      | Yes    |
| Body type codes not in the current catalogue vocabulary                                        | Unknown codes dropped; the criterion kept if at least one code remains, dropped otherwise (AC-50) | Yes    |
| Body type list with repeated codes                                                             | Repeats merged                                                                                    | No     |
| The same `k` twice in one list                                                                 | First occurrence kept, later ones dropped                                                         | Yes    |
| A requirement and a preference on one attribute whose target sets do not intersect (§6.3)      | Requirement kept, preference dropped; checked after the steps above                               | Yes    |
| `o` unknown or of the wrong type                                                               | `rel`                                                                                             | Yes    |
| `x` with a value other than `1`                                                                | Treated as absent                                                                                 | Yes    |
| `x` with no requirement after recovery                                                         | Ignored; omitted at the next write                                                                | No     |
| Unknown keys                                                                                   | Ignored (evolution)                                                                               | No     |
| `pc` / `pq` repeated or not a canonical positive integer                                       | Page 1                                                                                            | Yes    |
| `pq` with no requirement committed                                                             | Ignored; omitted at the next write                                                                | No     |
| `pc` / `pq` beyond the last page                                                               | Last page (§9.3)                                                                                  | No     |
| `q` invalid                                                                                    | M0.2 behaviour: empty query, silently (decided, OI-11); `s`, `pc`, `pq` still parsed and applied  | No     |

- The notice is non-blocking (results remain usable), visible, announced politely, and says that
  some parameters of the link were not valid and have been ignored or adjusted. It does not list
  technical details. One notice covers every issue of one load.
- **Proposal:** the URL is not rewritten on load; the next commit writes the canonical form of
  the recovered state, as the DC simulator does after an invalid URL. The notice disappears at
  that commit.

### 11.5 Navigation and context (FR-29)

- Opening a vehicle from a result (compatible or near-compatible) pushes the vehicle URL with the
  origin context, which now carries the whole committed Discovery state:
  `/veicoli/<id>?da=cerca&q=…&s=…&pc=…&pq=…` (each parameter only when not default).
- Vehicle Analysis' "‹ Risultati" and the browser's Back both restore query, criteria, objectives,
  modes, priorities, sort, pages and the near-compatible expansion (AC-35, AC-62), plus native
  scroll restoration where it applies (M0.2). Both must behave consistently (ADR 0001 Decision 4).
- The DC simulator forwards the same origin parameters, as in M0.2; returning through it keeps the
  Discovery state.
- Origin parsing reuses the Discovery parser with its recovery: an invalid `s` inside an origin
  keeps the origin as "search" with the recovered state; only an invalid `da` (or the M0.2 cases
  for `q`) turns it into a direct visit, as today. **Proposal:** no recovery notice on Vehicle
  Analysis; the return link carries the canonical recovered state.
- Transient states (open editors, drafts, disclosures, hover) are not restored (ADR 0001 Decision
  4, M0.2 criterion 8.3).
- A shared Discovery URL opened in a new session reproduces the same configuration; the results
  depend on the current catalogue (AC-36).

### 11.6 History policy (FR-30)

Decided (OI-03), following ADR 0001 Decision 2, where a page of results is treated as navigation:

| Event                                                                        | Results      | URL                      | History          |
| ---------------------------------------------------------------------------- | ------------ | ------------------------ | ---------------- |
| Typing the query                                                             | Updated      | Rewritten                | `replace` (M0.2) |
| Editing a draft that is incomplete or invalid                                | Unchanged    | Unchanged                | None             |
| Committing an objective; add, remove, mode switch, reorder, clear all, reset | Updated      | Rewritten                | `replace`        |
| Changing the sort                                                            | Updated      | Rewritten                | `replace`        |
| Expanding or collapsing the near-compatible section                          | That section | Rewritten (`x`)          | `replace`        |
| Explicit navigation to another page of a section                             | That section | Rewritten (`pc` or `pq`) | `push`           |
| Opening a disclosure or an editor                                            | —            | Unchanged                | None             |
| Opening a vehicle; "‹ Risultati"                                             | Destination  | Destination URL          | `push` (M0.2)    |

- Changes to the query, criteria, preferences, priorities, sort and expansion never add a history
  entry: after any number of them and no page navigation, one Back leaves Discovery for the
  previous page (AC-42, ADR principle 5).
- After page navigation, Back and Forward move between the pages visited, each entry restoring the
  complete committed state it was created with (AC-42). Since every history entry is a full URL,
  a criteria change made on page 3 replaces that entry with the new criteria at page 1; Back then
  returns to the page 2 entry with the criteria that were current when it was created. This is the
  intended consequence of URL ownership, not a separate rule.
- On Back or Forward within Discovery, drafts are discarded and the editors show the restored
  committed state (§5.7).

## 12. Empty states, invalid input and missing data

### 12.1 States (FR-31)

| State                                                       | Behaviour                                                                                                                                                                                      |
| ----------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| No criteria, no query                                       | Whole catalogue, price order, as M0.2 (AC-01); no "Compatibili" heading (AC-65)                                                                                                                |
| Query with no match                                         | M0.2 empty state ("Nessun veicolo", the query echoed), with the action to clear the query ("Mostra tutti i veicoli" as in M0.2); criteria, if any, are kept and the panel stays usable         |
| Query matches, no compatible, at least one near-compatible  | Compatible section states that no vehicle meets every requirement; near-compatible section expanded automatically (AC-28, AC-63)                                                               |
| Query matches, no compatible and no near-compatible         | One empty state with simple actions: edit the criteria (the panel stays available), "Cancella tutti i criteri", "Ripristina ricerca". No quantitative suggestion, no "nearest" vehicle (AC-30) |
| Compatible present, near-compatible present                 | Near-compatible collapsed with its count visible, or expanded if the user expanded it (AC-29, AC-62)                                                                                           |
| Compatible present, no near-compatible, requirements active | **Proposal:** the near-compatible section is not rendered                                                                                                                                      |
| No preference committed                                     | Ranking without `S` (price, name, ID after the near-compatible keys); explanations show only requirements                                                                                      |
| No requirement committed, preferences committed             | One list ordered by `S`, no headings, no near-compatible section (AC-65)                                                                                                                       |
| Requirement and preference on the same attribute            | Both shown in their sections; evaluated independently (§6.2)                                                                                                                                   |
| Requirement–preference conflict while editing               | Draft not committed; explanation in the editor; results and URL unchanged (§6.3, AC-46)                                                                                                        |
| Ties                                                        | Deterministic tie-breaks down to the ID (AC-33)                                                                                                                                                |
| Priority change                                             | Weights recomputed; `S`, `D_net`, membership and order follow; pages back to 1                                                                                                                 |
| Values exactly at thresholds                                | §7.10: requirement met at equality; `D_net = 0.25` admissible; `d_i = 1` excluded                                                                                                              |
| Malformed URL                                               | §11.4                                                                                                                                                                                          |
| Sort or page change                                         | §9.2, §9.3                                                                                                                                                                                     |

### 12.2 Invalid and incomplete input (FR-32)

- An editor rejects empty values, non-numbers, `NaN`, infinities, negative values, zero, values
  outside the domain, non-integers, ranges with `L ≥ U`, empty body-type selections and objectives
  that conflict with the attribute's criterion in the other mode; it never commits them (§5.7).
- Domains are defined by what a validated catalogue can contain, not by the values of the current
  illustrative catalogue (decided, OI-07). **Proposal for the bounds:**

  | Attribute     | Bound domain                                                                                  |
  | ------------- | --------------------------------------------------------------------------------------------- |
  | Price         | Integer euros, 1–10.000.000; the editor accepts `it-IT` grouping ("40.000"), rejects decimals |
  | Seats         | Integer, 1–`MAX_SEATS` (the catalogue validation limit, currently 9)                          |
  | Peak DC power | Integer kW, 1–5.000                                                                           |
  | Body type     | A non-empty subset of the current catalogue vocabulary (§5.6)                                 |

  The limits are defined once next to the calibration and enforced identically by the editors and
  the URL decoder. Vehicle attributes are not restricted to these bounds: a price or a power
  outside them is evaluated normally.

### 12.3 Missing data (FR-33)

| Missing attribute is used by | Effect                                                                    |
| ---------------------------- | ------------------------------------------------------------------------- |
| A committed requirement      | Vehicle excluded from both sections (AC-25); no credit can compensate     |
| A committed preference       | That satisfaction is 0; the vehicle is not excluded for it (AC-17, AC-25) |
| No committed criterion       | No effect on the evaluation (AC-25)                                       |
| The active manual sort key   | Vehicle placed after those that have it, in its section (AC-32)           |

No substitute value is ever invented. Explanations state the missing value (§10.4). In the
illustrative catalogue no evaluated attribute is missing; unit tests use synthetic projections
and browser tests the E2E fixture catalogue (§13.4).

## 13. Architecture in M0.3

Proportionate to M0.3: pure functions, the URL, local React state. No backend, no store, no
cache, no Web Worker, no new dependency. File names below are proposals (ADR 0001 open question
12); locations are binding in the sense of the layer they belong to.

### 13.1 Layers and modules

| Responsibility                                                                                                 | Layer               | Proposed module                                         |
| -------------------------------------------------------------------------------------------------------------- | ------------------- | ------------------------------------------------------- |
| Advanced state types, attributes, objectives, sort codes, invariants                                           | `src/scenarios/`    | `discoveryScenario.ts`                                  |
| Codec of `q` + `s` + pages: parse with recovery and typed issues (vocabulary as input), serialise              | `src/scenarios/`    | `discoveryScenario.ts` (or `advancedDiscoveryCodec.ts`) |
| Base64URL of ASCII/UTF-8 text with `TextEncoder`/`TextDecoder`, `btoa`/`atob`                                  | `src/scenarios/`    | inside the codec (no Node `Buffer`)                     |

| Criteria transitions: add, remove, switch mode, move, clear, reset, expansion; draft validation                | `src/application/`  | `discoveryCriteria.ts`                                  |

Production files stay directly in `src/scenarios/`, `src/application/` and `src/data/` so that the
ESLint layer guards of `AGENTS.md` apply; nesting deeper would need a review of the guards.

The evaluation is new application logic. It does not belong to, call or alter the M0.1 charging
engine; no charging mathematics is involved.

### 13.2 Evolution of `SearchScenario` and `OriginContext`

- `SearchScenario` (`{ query }`), `parseSearchScenario` and `SEARCH_QUERY_PARAM` stay as they are:
  the text part of Discovery.
- A new `DiscoveryScenario` composes them (shape is a proposal):

  ```ts
  type NumericAttribute = "price" | "seats" | "dc";
  type NumericObjective =
    | { op: "min"; lo: number }
    | { op: "max"; hi: number }
    | { op: "eq"; t: number }
    | { op: "range"; lo: number; hi: number };
  type Criterion =
    | { attribute: NumericAttribute; objective: NumericObjective }
    | { attribute: "body"; objective: { in: readonly BodyTypeCode[] } };
  type AdvancedDiscoveryState = {
    requirements: readonly Criterion[];
    preferences: readonly Criterion[];
    sort: SortOrder;
    nearExpanded: boolean;
  };
  type DiscoveryScenario = {
    search: SearchScenario;
    advanced: AdvancedDiscoveryState;
    pages: { compatible: number; near: number };
  };
  ```

  A constructor enforces the invariants: at most one criterion per attribute in each list,
  intersecting target sets for an attribute in both lists, bounds in the domain, `lo < hi` for
  ranges, non-empty sorted body sets of known codes, `nearExpanded` false without requirements.
  Every transition returns a valid state.

- `OriginContext`'s search variant holds a `DiscoveryScenario` instead of a `SearchScenario`.
  `parseOriginContext` keeps its M0.2 rules for `da` and `q` and adds the recovering parse of `s`,
  `pc`, `pq`. Callers (`routes.ts`, `VehicleCard`, `vehicleAnalysis.ts`, `dcSimulatorInteraction.ts`,
  `RicaricaPreview`) change type only. Existing origin tests keep passing; new ones cover the
  extended parameters.

### 13.3 Committed state, drafts and synchronisation

- `DiscoveryView` derives the committed `DiscoveryScenario` from the URL on every render, as M0.2
  does for `q`, and the results from it and the catalogue.
- Drafts live in the editor components. A commit builds the next committed state through the pure
  transitions and rewrites the URL with `history.replaceState`; page navigation uses
  `history.pushState` (§11.6). The exact synchronisation mechanism with the Next.js router is an
  implementation choice, provided `useSearchParams()` observes both.
- When the URL changes from outside, drafts are dropped (the M0.2 pattern of comparing with the
  last committed value applies).
- Results, sections, effective expansion, explanations and pages are derived, never stored (ADR
  0001 Decision 5).

### 13.4 Catalogue, vocabulary, missing attributes and the E2E fixture

- `BodyType` becomes an identifier type validated by the catalogue factory (§5.6) instead of a
  closed union; the vocabulary is derived from the catalogue in use. The five current codes and
  their labels are unchanged. Where labels live is [OI-16](#oi-16--body-type-labels-for-catalogue-defined-codes).
- The evaluation reads a projection: `DiscoveryAttributes = { listPriceEur?: number; seats?: number; bodyType?: BodyTypeCode; peakDcPowerKw?: number }`,
  built from a `CatalogueVehicle` by one function in `src/data/` or `src/application/`. Every
  field is optional in the projection so that missing data is representable; for the illustrative
  catalogue every field is present. Unit tests build synthetic projections.
- **E2E fixture (decided, OI-02).** Browser tests that need more than 20 results per section,
  missing attributes, or deterministic sorting and pagination scenarios use a dedicated synthetic
  catalogue fixture:
  - it is validated by the same catalogue factories as the illustrative catalogue;
  - it contains at least 21 compatible and 21 near-compatible vehicles for a stated set of
    criteria, vehicles without peak DC power, ties that exercise every tie-break, and at least one
    body type absent from the illustrative catalogue (AC-49);
  - the illustrative catalogue and its content remain unchanged;
  - the fixture is never reachable from a production build: no URL parameter, user interaction,
    route or runtime setting can select it (NFR-09, AC-71).
    How the fixture is selected for test builds, and how `CatalogueVehicle` represents a missing
    attribute, are [OI-15](#oi-15--e2e-fixture-selection-and-missing-attributes-in-the-catalogue-type).

### 13.5 Drag-and-drop without a new library

The stack has no sortable-list primitive (Base UI has none). Reordering is implemented with
native pointer events or the HTML drag-and-drop API inside the component, with the keyboard
alternative as a first-class control. If this proves insufficient, the need is reported (ADR 0001
§2); no library is added.

### 13.6 Larger catalogues later

The evaluation is linear in the number of candidates plus a sort; at thousands of vehicles it
remains cheap in the browser. M0.3 adds nothing for that case. What can be deferred: server-side
evaluation, indexing, memoisation (only with a measured need, ADR Decision 5), and catalogue
paging. The projection (§13.4) and the catalogue-derived vocabulary (§5.6) are the seams a future
data source (OpenEV Data) would feed.

### 13.7 ADR 0001 follow-up

M0.3 settles the URL format of Discovery (part of ADR open question 4: encoding, versioning,
partial recovery for this scenario), applies Decision 2's `push` for navigation to result pages,
and confirms that no Redux state is needed. When the implementation lands, ADR 0001 should be
revised to record these as resolved for Discovery; the comparison scenario's format stays open.

## 14. Non-functional requirements and accessibility

### 14.1 Non-functional

- **NFR-01 Determinism.** The same URL and catalogue always give the same sections, order and
  pages; parsing and serialisation are deterministic. Sorting uses `Intl.Collator`/`localeCompare`
  with `it-IT`; server and client must use the same comparator so that server-rendered and
  hydrated orders agree.
- **NFR-02 Purity and layering.** Evaluation, ranking, transitions and codec are pure TypeScript
  without React, Next.js, Redux or browser-only APIs; ESLint guards pass.
- **NFR-03 No dependency** outside ADR 0001; no change to the stack.
- **NFR-04 Engine unchanged.** No change in `src/domain/` or `src/calculations/`; M0.1 tests
  unchanged and passing.
- **NFR-05 Performance.** Results are recomputed on each committed change without perceptible
  delay on the current catalogue and the E2E fixture; no cache without a measurement.
- **NFR-06 Robustness.** No URL, input or catalogue content crashes the page.
- **NFR-07 Precision.** Unrounded computation, rounded presentation, boundary rule of §7.10.
- **NFR-08 Visual identity.** Livrea Consolidated as in §10.3; tokens only.
- **NFR-09 Fixture isolation.** The E2E fixture catalogue is not part of what a production build
  can serve (§13.4).

### 14.2 Accessibility (FR-34)

- Every new control is reachable and operable by keyboard in a sensible order, with a visible
  focus indicator and no trap: add, editors (operator, bounds, body-type selection), behaviour
  toggle, remove, move up/down, clear, reset, sort, section toggle, pagination, disclosure.
- Reordering by keyboard produces the same state and URL as by pointer (AC-41) and is announced.
- Controls have accessible names that include the criterion and, where an attribute appears in
  both modes, the mode they act on ("Sposta su Prezzo, requisito", "Rimuovi Posti, preferenza");
  the two bounds of a range have distinct names ("minimo", "massimo"); the section toggle exposes
  its expanded state and count; pagination is a navigation landmark per section with the current
  page marked.
- Focus is managed: after adding a criterion, to its editor; after removing one, to a sensible
  neighbour; after a page change, to the section's heading.
- Invalid values, invalid ranges and conflicts are announced with the field they concern; the URL
  recovery notice is a polite status.
- No information by colour alone: violations carry an icon and words; the selected behaviour and
  operator have text.
- Text contrast meets the Livrea Consolidated ratios; `lang="it"` stays.
- A manual accessibility review of the new controls, with at least one screen reader and browser
  combination, is recorded before acceptance (§16).

### 15.3 Mathematical edge cases to cover in unit tests

The matrix rows AC-11–AC-27 and AC-51–AC-61 cover the model. In addition, unit tests should cover:

- Each satisfaction function inside the ideal set, at both boundaries, at `σ/2` and `σ` on each
  side, and far outside; continuity at the boundaries; independence from the catalogue and from
  the weight.
- Gaussian scales derived from the relevant boundary for price (`0.20 · L` below, `0.20 · U`
  above), including ranges where the two sides differ.
- Weights for n = 1–4: values, strict decrease, sum 1 (within floating tolerance).
- `d_i` at `Δ = 0`, between, `Δ = τ` (`d = 1`), `Δ > τ` (capped), on each side of a range and an
  exact objective.
- Credits at `φ = 0`, between, at `κ`, beyond `κ`; no credit for every non-eligible objective.
- `D_net` exactly 0.25 (admissible) and just above (excluded); negative `D_net`; `D_net` with one
  and with several violations; weights normalised over satisfied and violated requirements.
- Requirements met at equality for every operator.
- The intersection check on every operator pair, at touching boundaries and at the seats domain
  limits.
- The monotonicity property on a grid of attribute values for fixed criteria (§7.11).
- Ties of `S` and `D_net` produced by different arithmetic paths (quantisation, §7.10).
- No criteria; only preferences; only requirements; both lists full (eight criteria).
- Codec: round trip of every state shape; canonical output; every recovery row of §11.4.

### OI-15 — E2E fixture selection and missing attributes in the catalogue type

The fixture is decided (OI-02); two implementation questions follow from it.

1. **Selection.** The E2E suite runs against a production build (ADR 0001 §7), and the existing
   M0.2 rows assert the illustrative vehicles. The fixture must therefore be used by a separate
   test build or a separate test server, selected at build time and absent from the production
   bundle. **Proposal:** a build-time switch read only in `src/data/vehicles.ts`, with the fixture
   data under the test sources; a second Playwright project or web server for the fixture rows; a
   code-review check and a unit test that the production module graph does not include the
   fixture (AC-71). Cost: a second build in CI.
2. **Missing attributes.** `CatalogueVehicle` requires every evaluated attribute, so the fixture
   cannot contain a vehicle without peak DC power (AC-32) until the type can represent one. This
   is a `src/data/` change, outside the M0.1 engine, but it reaches cards, Vehicle Analysis and the
   DC simulator entry point. **Proposal:** add a charging variant without DC data, rendered on
   cards as "Potenza DC non disponibile", and keep other attributes required in M0.3. **Product
   part:** how Vehicle Analysis and the simulator present a vehicle without DC data. Such vehicles
   exist only in the fixture in M0.3, so a minimal treatment (no simulator link) would suffice.

### OI-16 — Body-type labels for catalogue-defined codes

Every selectable code needs an Italian label (§5.6). Today labels are a presentation map keyed by
the closed `BodyType` union, which would have to change for each new code. Options: (1) keep a
presentation map and accept that a new catalogue code needs a label added there; (2) let the
catalogue define its body-type vocabulary with labels, validated at load time. Either keeps codes
and labels separate. **Proposal:** option 2, with a catalogue validation error when a vehicle uses
a code that has no label, so that the failure is loud at build time and never shows a raw code.

### OI-17 — Default preference operators and the mode of a second criterion

The approved decisions fix the default requirement objectives (price maximum, seats minimum, DC
minimum) but not the default preference operators, which matter most for peak DC power since it
starts as a preference. **Proposal:** price maximum, seats exact value, DC minimum, matching the
first draft's preference directions (§5.1). Also proposed, not approved: when the default mode is
already used by an attribute, "Aggiungi criterio" adds the attribute in the other mode (FR-03),
and while automatic expansion applies the section toggle is not offered (§9.4).

## 18. Out of scope

- Structured comparison between vehicles; the comparison selection and its UI.
- External catalogues or datasets (OpenEV Data); changes to the illustrative catalogue's content.
- User accounts; saving searches on a server; browser storage of searches.
- Automatic quantitative suggestions to relax requirements; user-editable tolerances, scales or
  credits ("Rendi flessibile").
- Favourable credits other than the maximum-price and minimum-DC rules of §7.8; a categorical
  similarity matrix between body types.
- New range or trip simulations; estimates (`stima`); trip stops.
- Charging times deduced from peak DC power; the practical "Tempo di ricarica" criterion.
- Criteria other than the four attributes of §5.1 (boot space, daily use, long trips, home
  charging, ...); needs typed into the search field.
- Manual weights or percentages.
- View modes (Schede/Elenco/Differenze), "Ricerche frequenti", "Approfondisci", the "last change"
  notice with undo.
- New Vehicle Analysis or simulator features beyond forwarding the Discovery context.
- M0.2 open question 5 (accent and separator matching).
- Responsive or mobile layouts and dark theme (not designed).
- Architectural refactoring not required here: no backend, no Redux store, no caching layer, no
  change to the M0.1 engine.
- Comprehensive accessibility validation (DEBT-11, pre-release part).

## 19. Completion and acceptance criteria

M0.3 is complete when all of the following hold and are recorded with evidence. None holds at
the time of writing.

1. **Prerequisites.** The DEBT-11 basic smoke test was recorded and the M0.3 design iteration was
   reviewed before the new Discovery UI was implemented; the open issues of §17.2 are decided and
   the decisions recorded in this document.
2. **Acceptance matrix.** Every AC of the matrix has at least one test at the level stated there,
   named with its AC identifier, passing in Vitest and, for browser rows, in Playwright Chromium
   and Firefox; manual rows are recorded.
3. **Requirements without an AC.** Single removal (FR-06) is tested; the calibration is one
   documented module with tests (FR-17).
4. **Engine and architecture.** No change in `src/domain/` or `src/calculations/`; M0.1 tests
   unchanged and passing; no new dependency; no Redux; ESLint guards pass; results derived, not
   stored; the E2E fixture is absent from production builds.
5. **URL.** Every M0.2 Discovery, vehicle-with-origin and simulator URL keeps its meaning; the
   canonical form of §11.2–11.3 is produced; every case of §11.4 behaves as specified.
6. **Regression.** All M0.2 Playwright rows pass; E2E-051's Discovery evidence is re-recorded and
   reviewed; `npm run check` and `npm run test:e2e` succeed; CI's required checks are green.
7. **Accessibility.** The checks of §14.2 pass in Playwright where automatable; a manual review of
   the new controls with at least one screen reader is recorded; defects are fixed or entered in
   the register with a decision.
8. **Visual identity.** At 1440 px Discovery follows §10.3 and the reviewed design iteration,
   checked against Livrea Consolidated.
9. **Documentation.** README status, the documentation index, this specification's status and
   open issues, the ADR revision of §13.7, maintenance plan O6 and the technical debt register are
   updated.
10. **Review.** An independent final review against this specification and the matrix, and the
    product owner's approval of the closure.
