This is the TD-03 migration inventory for the completed M0.2 vertical slice. Playwright,
Chromium and Firefox projects cover all 52 browser-facing rows; the remaining E2E-047 is intentionally retained in Vitest. Independent chart and M0.2-scoped Livrea visual reviews were accepted on 2026-11-24. Behavioural parity is measured by the rows below, not by reproducing the legacy script's 154 implementation-level checks one for one.

## Scope and baseline

- Baseline: `dev` at `8d7f7a2` (2026-11-18).
- Legacy evidence: the complete `scripts/verify-dc-simulator-url.mjs` at that baseline.
- Product evidence: M0.2 acceptance criteria in
  [`m0.2-first-vertical-slice.md`](../milestones/m0.2-first-vertical-slice.md#7-acceptance-criteria).
- Planned locations: Playwright tests under `e2e/`; this matrix at
  `docs/testing/e2e-traceability.md`.
- Required projects: Chromium and Firefox. WebKit is deferred; Firefox is not optional and no row
  may be skipped merely because an engine exposes different browser APIs or event timing.

Coverage terms:

- **Legacy**: the legacy browser script directly exercises the complete observable behaviour.
- **Partial**: the script or existing Vitest tests protect only part of the observable behaviour.
- **Vitest**: the accepted requirement is pure logic and existing Vitest coverage is the
  appropriate level; the row records why no browser test is proposed.
- **None**: no existing automated check directly protects the observable behaviour.

Rows marked **Migrated** name the executable test and record its Chromium and Firefox evidence. Independent visual review has approved E2E-043, E2E-044 and E2E-051; no Playwright row remains **Partial** or **Planned**. Test names are deliberately behavioural;
implementation may group several rows in one spec as long as reporting keeps the row IDs
traceable.

## Browser/API interpretation

The matrix intentionally keeps these concepts separate:

1. **Browser API availability** is a capability of the engine/build under test. The suite records
   whether native `window.navigation` exists; it does not fail Firefox merely for lacking an API
   and does not fake native availability.
2. **Application compatibility** is the outcome for the supported path. When the Navigation API
   exists, the bypass rewrite in E2E-030 must be observed immediately. When it does not, the
   documented router/fallback behaviour in E2E-031 is required, including the known delayed
   observation of a rewrite that bypasses the router patch.
3. **Test implementation** may use `page.evaluate` or an init script to create an external History
   API change or force API absence. Those are setup mechanisms, not application behaviour. Engine
   timing differences may change waiting strategy but not the required outcome.

A cross-browser mismatch in an intended outcome is recorded as a possible application
compatibility defect and requires a separate decision; it is not resolved by weakening or
skipping the Firefox expectation.
